## The problem with hash-mod-N

Say you spread cached entries across `N` servers by sending each key to
`hash(key) % N`. It works — until `N` changes. Add or lose one server and the
*modulus* changes, so `hash(key) % N` lands somewhere new for **almost every
key at once**. About `(N-1)/N` of your keys move in an instant.

For a [cache](/topics/systems/caching) that's the worst case: a rescale becomes a
near-total **miss storm**, and the backend you were protecting takes the full
load right when you were trying to grow.

<Callout type="warning">
The cost isn't adding a server — it's that mod-N rehashes the whole keyspace.
You want a scheme where changing N moves only the keys it has to.
</Callout>

## The ring

<Term>Consistent hashing</Term> fixes this by hashing **nodes and keys onto the
same** <Term>hash ring</Term> — a circular hash space that wraps around. A key
is owned by the first node you reach going clockwise from the key's position.

Now adding a node only captures the keys in the arc from its counter-clockwise
predecessor up to itself (the keys that now reach it first); removing a node hands
its arc to its clockwise successor. Either way you move
about `1/N` of the keys instead of `(N-1)/N`. That `1/N` bound is the whole point
(Karger et al., 1997).

## Balancing with virtual nodes

One position per node leaves uneven gaps, so some nodes own much larger arcs —
and more keys — than others. The fix is <Term id="virtual node">virtual
nodes</Term>: give each physical node many positions on the ring. The arcs
average out, and load evens across nodes (this is how Dynamo-style stores do it
in practice).
