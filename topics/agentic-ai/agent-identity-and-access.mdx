## One injection, one breach

The last lesson set a rule: least privilege limits the damage of any attack
that gets through. This lesson makes it concrete on Google Cloud.

Access on Google Cloud is managed by **IAM**. A **principal** (a user, a group, a
workload) is granted a **role** (a set of permissions) on a resource, such as a
project or a single bucket, through an **allow policy**. A **service account**
is a principal for software rather than a person.

Many first agents run as a service account that some other workload already
uses, with a broad role on the project. That works, until the agent reads a
document with an injected instruction. The agent can then do anything that
account can do: read the HR database, change production, reach into other
projects. Nothing in the logs says which agent did it, because several share
the account.

Three changes shrink that blast radius, and they build on each other.


## Step 1: give the agent its own identity

<Term id="agent identity">Agent Identity</Term> gives each agent a dedicated
principal on Google Cloud. It is based on <Term id="spiffe">SPIFFE</Term>, an
open standard for workload identity: each agent gets a cryptographic identity
with an X.509 certificate that Google Cloud provisions and manages on the agent.
Agent Runtime, Gemini Enterprise, Cloud Run and GKE support it.

Compared with a shared service account, an agent identity:

- **belongs to one agent.** Agent identities are not shared by multiple
  workloads by default, so a grant to one reaches only that agent.
- **is the principal you grant to.** You grant roles directly to the agent's
  identifier, so each agent's access is set on its own.
- **shows up in audit logs.** The logs record the agent and, when it acts for
  a user, that user, so you can tell which agent did what.
- **is harder to steal.** It cannot be impersonated, it allows no long-lived
  keys, and its access tokens are bound to the agent's certificate, which is
  designed to stop a stolen token being reused elsewhere.

For agents governed by Agent Gateway, Context-Aware Access enforces that binding
by default. The agent reaches Google
Cloud APIs and Agent Gateway over mTLS (mutual TLS, where both sides present
certificates) with certificate-bound tokens. Agent Gateway terminates mTLS, so
beyond it the binding is carried by DPoP (Demonstrating Proof-of-Possession, RFC
9449): proofs signed with the agent's private key, which Context-Aware Access
checks. Google's words for the result: "compromised tokens are useless outside
of their intended, trusted runtimes."

## Step 2: grant only what the tools need

An identity of its own does nothing for the blast radius if it holds a broad
role. Work out access from the tools:

1. **List what each tool touches.** The invoice tool reads one bucket; the
   lookup tool reads one dataset. Nothing writes.
2. **Grant the narrowest role on the narrowest resource.** A read-only role on
   that bucket, and one on that dataset, granted to the agent's principal.
   Avoid project-wide grants and the broad basic roles (Owner, Editor), which
   reach most resources in the project.
3. **Assume the injection will succeed.** Ask what a hijacked agent could do
   with exactly these grants. Here: read invoices and one dataset, nothing
   else.

A permission error is a cheap, visible failure that you fix by adding one
narrow grant. Broad access fails silently, on the day someone exploits it.

## Step 3: cap the reach with a boundary

Grants drift. Another team adds a role for a new feature; someone grants a
broad role to debug and forgets it. A
<Term id="principal access boundary">Principal Access Boundary</Term> (PAB)
policy guards against that. It defines the resources the principals it covers
are **eligible** to access. If a resource is outside the boundary, they cannot
reach it (for the permissions the boundary supports), regardless of the roles
they have been granted. A boundary applies to a set of principals that includes
the agent, rather than being written into each role grant.

**Roles grant; a boundary caps.** A PAB policy can only block or not block; it
never grants. So you use both:

- the role grants say what the agent can do;
- the boundary says the furthest it can ever reach, such as the finance project
  only, whatever is granted later.

Three limits to know. By default, with no PAB policy, a principal is eligible
to access any Google Cloud resource; the cap exists only once you add one. A
PAB policy only blocks access that involves the permissions it supports, so it
backs up narrow grants rather than replacing them. And when several PAB
policies apply to the same principal, for example set at different scopes,
their eligible resources combine: a finance-only boundary does not cancel
another applicable policy that also makes HR eligible. The finance-only cap
holds only if every policy that applies allows only finance.

<Callout type="warning">A common trap: broad basic roles "to avoid permission errors". Owner reaches most resources in the project, so a single injected instruction can read, change or delete any of it. Grant the narrowest roles the tools need, and add a boundary that covers the agent.</Callout>

## Try it: which doors can the agent open?

In **Which doors can the agent open?**, an invoice contains an injected request
for Finance exports, HR payroll and Production backups. The agent attempts
those reads as well as its intended invoice read. These attempts are scripted:
IAM checks permissions; it does not decide whether the text is malicious.

Start with an invoices-only read grant and the Finance boundary on. Predict
which doors will open if someone adds an organization-wide read grant. Choose
an answer, then press **Add broad read grant**. Next, press **Remove all grants**
and watch what happens while the boundary stays in place.

<Simulation id="access-boundary-explorer" />

**Explain it:** Why did the broad grant open Exports but leave Payroll closed?
Why did Invoices close when you removed all grants, even though it stayed
inside the Finance outline?

This fixture uses four private Cloud Storage buckets in three projects under
one organization. The read role is `roles/storage.objectViewer`, granted on
the Invoices bucket or inherited from the organization. Each attempt reads one
existing object using `storage.objects.get`, which PAB enforcement version 1
covers. Uniform bucket-level access is enabled; there are no public grants,
ACL grants, other role grants, deny policies or conditional bindings. The map
shows these object reads, not every permission in the role or every IAM check.

There is exactly one applicable Finance PAB when the boundary is on, and none
when it is off. With several applicable PABs, eligible resources combine by
**union**: another policy can make HR eligible. The outline represents resource
eligibility, not a network firewall.

## Recap

- Give each agent its own identity: per-agent grants, per-agent audit, an
  identity not shared by default, and no long-lived keys.
- Grant the narrowest roles on the narrowest resources its tools need, and
  design as if prompt injection will succeed.
- Roles grant; a Principal Access Boundary caps. Use both, so a mistaken grant
  later still cannot reach past the boundary.
