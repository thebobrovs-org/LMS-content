## Why retrieval decides the answer

<Term id="rag">Retrieval-augmented generation (RAG)</Term> gives a model
content it was never trained on: before the model answers, the system finds the
most relevant passages in your documents (the corpus) and places them in the model's
context. In an agent, retrieval is usually one tool (topic 3.2): the model
proposes a search, the runtime runs it, and the passages come back as the tool
result.

The model can only be as right as what it reads. If retrieval misses the
passage that holds the answer, the best model in the world answers "I don't
know" or guesses. If retrieval delivers an outdated passage, the model faithfully
repeats it. Retrieval quality caps answer quality, so most RAG problems are
fixed in the pipeline, not in the prompt.

## The six stages, and the decision at each

Retrieval finds passages by meaning, not by keywords. Each chunk and each
question is turned into a vector, and closeness between two vectors is a
similarity score: chunks that mean nearly the same thing as the question score
high, even when they share no words with it.

| Stage | What happens | The decision you make |
|---|---|---|
| **Ingest** | Load the documents and extract their text, including from scans and tables | Which sources, how to parse them, how often to refresh |
| **Chunk** | Split each document into passages | Chunk size and overlap |
| **Embed** | Turn each chunk into an <Term id="embedding">embedding</Term>, a vector that represents its meaning | Which embedding model |
| **Index** | Store the vectors, with metadata such as source and date, so they can be searched fast | Which vector database, which metadata |
| **Retrieve** | Embed the question, find the chunks whose vectors are closest, optionally rerank them, keep the <Term id="top-k">top-k</Term> | How many to keep, whether to rerank, what to filter on |
| **Generate** | The model answers from the retrieved chunks, ideally citing them | How to instruct and cite |

The first four stages run ahead of time, when documents are added or change.
The last two run on every question.

## Three knobs that decide what the model sees

**Chunk size.** Small chunks match a question precisely but can cut a rule off
from its exception. Large chunks keep context together but mix in unrelated
text, which weakens the match and spends tokens. RAG Engine, for example,
defaults to 1,024-token chunks with a 256-token overlap, so neighbouring chunks
share text across the cut.

<Flashcard id="chunk-size-tradeoff" objective="tune-retrieval" front="What do small and large chunks each risk?" back="Small chunks can split a rule from its exception, so part of the answer never reaches the model. Large chunks mix the relevant passage with unrelated text, which blurs the match and costs more tokens per call." />

**Top-k.** How many retrieved chunks reach the model. Too few and the answer
can miss a second relevant chunk. Too many and near-misses crowd the context,
compete with the right chunk and cost tokens on every call.

**Reranking.** Vector similarity is fast but rough. A
<Term id="reranking">reranker</Term> takes a wider set of candidates (say, the
top 20) and rescores each one against the question with a stronger relevance
model, so the few chunks that reach the model are the most relevant ones. RAG
Engine offers two: the ranking API, a dedicated reranker that responds in under
100 ms, and an LLM reranker that asks Gemini to judge relevance and takes one to
two seconds. Reranking measures relevance, not truth: an outdated passage that
answers the question exactly still ranks first.

**Hybrid search.** Vector similarity matches meaning, so it can miss an exact
token such as a product code, an error number or a rare name; keyword search
finds those tokens but misses paraphrases. <Term id="hybrid search">Hybrid search</Term> runs both and merges the two ranked lists. Agent Retrieval
(formerly Vector Search 2.0) merges them with <Term id="reciprocal rank fusion">Reciprocal Rank Fusion</Term> (RRF): each result scores by its rank in
each list rather than by its raw score, so the scores of two different methods
never have to be compared, and a weight (an alpha from 1.0, purely semantic,
to 0.0, purely keyword) leans the blend toward one side. The fused list can
then go to the **Agent Platform ranking API**, the dedicated reranker described
above, for reranking.

<Flashcard id="hybrid-search-rrf" objective="tune-retrieval" front="When does hybrid search help, and how does Agent Retrieval merge its two result lists?" back="When questions carry exact tokens (product codes, error numbers, rare names) that embeddings blur, or paraphrases that keyword search misses. It runs semantic and keyword search and merges the lists with Reciprocal Rank Fusion, which scores each result by its rank in each list; a weight leans the blend toward one side. The Agent Platform ranking API can then rerank the fused list." />

## Try it: a stale policy in the corpus

Two numbers tell you whether retrieval found the right material. Call the
chunks a correct answer needs the **relevant** ones. Then, for the top-k chunks
that reach the model:

- **Precision@k** is the share of those k chunks that are relevant: how clean
  the catch is.
- **Recall@k** is the share of all relevant chunks that made the top k: how
  complete it is.

Both are standard information-retrieval measures, and they pull against each
other: a bigger k can only keep or raise recall, and usually lowers precision.

In **Grounded but wrong: the right catch**, the corpus is a pond and every
chunk is a fish, ranked by how similar its meaning is to one question: "How
many days do I have to return an item?" Two versions of the same policy swim
there: a 2024 FAQ (60 days, now superseded) and the current 2026 policy (30
days, with a final-sale exception). The net is your top-k, the bucket is what
the model reads, and the precision and recall meters are drawn as the fish you
caught. An answer drawn from the retrieved chunks is called **grounded**; the
question is whether grounded also means right.

Before you cast, predict: the default net catches the top 3 medium chunks, and
the current 30-day policy is among them. What will the agent answer?

<Simulation id="rag-retrieval-tuner" height={1000} />

What you should see:

- **The default answer is grounded but wrong.** Recall is 1 of 1: the 2026
  policy is in the bucket. But precision is 1 of 3, and the 2024 FAQ ranks
  first, because it is about exactly this question and similarity measures
  meaning, not which version is current. The model reads it first, cites it
  faithfully and says 60 days.
- **Reranking does not save you.** The old FAQ answers the question just as
  directly as the new policy, so a reranker keeps it on top.
- **A bigger net does not save you either.** Raising top-k adds chunks and
  tokens to every call, but the old FAQ still ranks first.
- **The metadata filter fixes it.** Throw superseded documents back before the
  search and the 2026 policy is the first one the model reads: 30 days, except
  final-sale items. Precision can stay low; in this exercise the off-topic
  chunks left in the net only cost tokens.
- **Chunk size moves recall.** With small chunks, the final-sale rule sits in
  its own chunk, so there are two relevant chunks. At top 3 without reranking
  it misses the net: recall is 1 of 2 and the answer is right but incomplete.
  Reranking lifts it back in.

Explain it: at the default setting recall was perfect, so why was the answer
wrong, and why did the filter fix it when a bigger net did not?

## Grounded but wrong

A **grounded** answer is one the model drew from retrieved sources rather than
from its training. Grounded is not the same as correct. When the source is
stale, superseded or simply wrong, a faithful model repeats it, often with a
citation that makes the error look trustworthy.

Recognise it by the pattern: the answer quotes a passage that really exists in
your corpus, and that passage is out of date. An answer with facts that appear
in no document is a different failure, a model inventing content.

Fix it where it starts, in the data:

1. **Remove or archive superseded documents**, and make re-ingestion part of
   publishing a new version.
2. **Add metadata** such as `status` (current or superseded),
   `effective_date` or `region` when documents are ingested, and store it with
   each vector when they are indexed.
3. **Filter retrieval on that metadata**, so only current documents are
   searched. RAG Engine's metadata filter is in Preview at the time of
   writing: v1beta1 API only, not in serverless mode, and it needs a metadata
   schema on the corpus.

An instruction such as "prefer the newest document" is a weak patch: the model
can only follow it if both versions are retrieved and each chunk shows its
date, and it does nothing to stop retrieval from feeding the old one.

## Choosing a backend

Google Cloud offers three backends, from most managed to most control.

Each lane below is one backend, and each step runs one lane through every
pipeline stage. Before you step, predict which lane lets you chunk the documents yourself
while Google runs the index.

<Simulation id="rag-backend-lanes" />

- **Agent Search** (formerly Vertex AI Search) is an out-of-the-box RAG
  system. It handles parsing, chunking, embedding and indexing over your
  websites and documents, and its generated summaries come with citations and
  links. Start here.
- **<Term id="rag engine">RAG Engine</Term>** is <Term id="agent platform">Agent Platform</Term>'s managed RAG
  pipeline, built around a corpus you import files into. You configure the
  pipeline: chunk size and overlap, the embedding model, the vector database
  (its managed default, Vector Search, Feature Store, or third-party vector
  databases such as Pinecone or Weaviate), top-k and reranking.
- **Vector Search** is a vector database you query directly. You supply the
  embeddings and build ingestion, chunking and ranking yourself. **Agent
  Retrieval** (formerly Vector Search 2.0) sits a little closer to managed: it
  stores your documents with their vectors, can generate the embeddings with
  built-in models or take yours, and offers hybrid search and reranking, while you still prepare
  and chunk the documents you load and write the query. Choose either when you need direct control of how
  vectors are stored and queried; custom embeddings alone are not a reason,
  since Agent Search accepts them too.

Each lane down buys control and costs engineering time. Move down only for a
need the lane above it cannot meet.

A retrieval call to RAG Engine with a reranker looks like this (Python, Vertex
AI SDK):

```python
from vertexai import rag

config = rag.RagRetrievalConfig(
    top_k=10,  # candidates to rerank; all ten come back in reranked order
    ranking=rag.Ranking(
        rank_service=rag.RankService(model_name="semantic-ranker-default@latest"),
    ),
)

response = rag.retrieval_query(
    rag_resources=[rag.RagResource(rag_corpus=corpus_name)],  # your corpus's resource name
    text="How many days do I have to return an item?",
    rag_retrieval_config=config,
)
```

Pass only the first few reranked chunks to the model.

In an agent, the same retrieval sits behind a tool, so the model decides when
to search and the runtime runs it.

<Callout type="warning">Product names in this area changed in 2026: Vertex AI Search was renamed Agent Search on 22 April, Vector Search 2.0 was called Agent Retrieval by mid-May, and RAG Engine now runs on Gemini Enterprise Agent Platform. Some current pages, older documentation and practice questions still use the former names.</Callout>
