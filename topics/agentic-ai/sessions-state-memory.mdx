## Where does each piece of data belong?

Your support agent from the previous lesson now has real users. A customer
orders a lamp on Monday, asks you to ship it to their Lyon office, and picks
French as their reply language (the agent has a `set_language` tool for that).
On Thursday they come back. What should the agent still
know, and where should it have kept it?

Get this wrong in one direction and the agent feels broken: it forgets what was
said three turns ago, or asks for the language again. Get it wrong in the other
and it costs tokens on every call and keeps personal data it never needed. ADK
gives you three places, and the decision is which one each value belongs in.

## Sessions: one conversation

A <Term id="session">session</Term> is one conversation thread between a user
and your agent. It holds two things:

- **Events**, the history: every user message, model response, tool call and
  tool result, in order. Each model call reads them, which is how the agent
  remembers what was said three turns ago.
- **<Term id="session state">State</Term>**, a key-value scratchpad the agent
  and your code read and write during the conversation, such as
  `order_id = "B-77"`.

A `SessionService` stores sessions. ADK ships three kinds:

| Service | Where sessions live | Use it for |
|---|---|---|
| `InMemorySessionService` | The process's memory; **lost on restart** | Local development and tests |
| `DatabaseSessionService` | A relational database you run (PostgreSQL, MySQL, SQLite) | Persistent sessions you manage |
| `VertexAiSessionService` | Agent Platform Sessions, managed by Google Cloud | Production on Google Cloud without running a session store |

Agent Platform is Google Cloud's managed platform for building and running
agents, and Agent Platform Sessions is its managed session store. In production,
use a persistent service. An in-memory service on a platform that runs several
copies of your app, such as Cloud Run (Google Cloud's serverless container
service), loses the conversation whenever a request lands on another copy or a
copy restarts. Agent Platform Sessions removes the need to run your own store;
every session has a time to live (365 days unless you set one).

On Google Cloud, `DatabaseSessionService` usually points at **Cloud SQL**
(managed PostgreSQL or MySQL): it takes a database URL, so the same code runs on
SQLite locally and Cloud SQL in production. Firestore and Memorystore (managed
Redis) are in scope too, but as data stores your **tools** read and write, such
as a customer profile in Firestore or a cache in Memorystore. ADK's
documentation lists no session service for either, so do not plan on one.

## State scopes: how far a value reaches

The prefix on a state key sets its scope:

| Key | Scope | Example |
|---|---|---|
| `order_id` (no prefix) | This session only | The order being discussed |
| `user:language` | Every session of this user, in this app | A preference the user set |
| `app:support_hours` | Every user and session of the app | A global setting |
| `temp:api_raw` | This invocation only (one turn); never persisted | A scratch value between two tools |

Your code reads and writes one merged state; the session service stores each
key where its prefix says. A tool writes state through its `tool_context`:

```python
from google.adk.tools.tool_context import ToolContext

def set_language(language: str, tool_context: ToolContext) -> dict:
    """Sets the language the agent replies in, for all of this user's conversations.

    Args:
        language: An ISO language code, for example "fr".
    """
    tool_context.state["user:language"] = language
    return {"status": "success", "language": language}
```

Scopes beyond the current session persist only if the session service does:
with `InMemorySessionService`, a `user:` key disappears on restart along with
everything else. ADK's state guide says these scopes persist with the database and Vertex AI
session services, but ADK's own tests of shared `user:` and `app:` state cover
`DatabaseSessionService` only, so on Agent Platform Sessions check that a
`user:` key written in one session reads back in a new one before you rely on
it.

## Memory: what lasts across conversations

A session ends. Some of what the user said is worth keeping: where they work,
what they bought, what went wrong last time. That is **long-term memory**, and
ADK reaches it through a memory service. Session and state are short-term memory
for one conversation; memory is a searchable store across many.

<Term id="memory bank">Memory Bank</Term> is Agent Platform's managed long-term
memory, and ADK connects to it with `VertexAiMemoryBankService`. It does not
store transcripts. It:

- **Extracts** the meaningful facts from a conversation with an LLM, and
  **consolidates** them with what it already holds, so a changed fact updates a
  memory instead of piling up duplicates.
- **Isolates** memories per scope, such as the app (or agent) and the user, so one
  user's memories never reach another's conversation. Every session therefore
  needs a user id.
- **Retrieves** either all memories for a scope or only the ones most relevant
  to the current message.

You can steer what it extracts with your own topics and few-shot examples, let
the agent write a memory directly when it decides one is worth saving, and set a
time to live on memories. A default time to live is counted from each
creation or update, so a memory that consolidation keeps updating stays longer
than one written once.

So on Thursday the agent starts a new, empty conversation, yet still replies in
French (a `user:` key its own tool wrote) and offers the Lyon office (a fact
Memory Bank extracted and recalled). The order id from Monday is not in the new session, as it
should be. It has not been deleted: Monday's session is still stored, and your
app can load and resume it until you delete it or its time to live expires.

## Wire Memory Bank into an ADK agent

Three pieces, each a choice:

1. **The service.** Pass a `VertexAiMemoryBankService` to the `Runner`, or start
   `adk web` with `--memory_service_uri="agentengine://<agent_runtime_id>"`. It
   needs an Agent Runtime instance in your project, though the agent itself need
   not be deployed there. Agent Runtime is Agent Platform's managed runtime for
   agents; it was formerly called Agent Engine, which is why the parameter is
   `agent_engine_id`.
2. **When to save.** Memories are generated when you send session data to the
   service, for example at the end of each turn or session. An after-agent
   callback that calls `add_session_to_memory` does it automatically.
3. **How to recall.** `preload_memory` retrieves relevant memories at the start
   of every turn; `load_memory` is a tool the model calls only when it decides
   memory would help. Preload is predictable and costs a lookup on every model call in a turn; load
   saves lookups but depends on the model asking.

```python
from google.adk.agents import LlmAgent
from google.adk.agents.callback_context import CallbackContext
from google.adk.memory import VertexAiMemoryBankService
from google.adk.runners import Runner
from google.adk.sessions import VertexAiSessionService
from google.adk.tools import preload_memory

async def save_to_memory(callback_context: CallbackContext):
    await callback_context.add_session_to_memory()

root_agent = LlmAgent(
    name="support_agent",
    model="gemini-flash-latest",
    instruction="Help customers with orders. Use what you remember about them.",
    tools=[preload_memory],
    after_agent_callback=save_to_memory,
)

runner = Runner(
    agent=root_agent,
    app_name="store-support",
    session_service=VertexAiSessionService(
        project="PROJECT_ID", location="LOCATION", agent_engine_id="AGENT_RUNTIME_ID"
    ),
    memory_service=VertexAiMemoryBankService(
        project="PROJECT_ID", location="LOCATION", agent_engine_id="AGENT_RUNTIME_ID"
    ),
)
```

The Runner's session service creates and loads each session by `app_name`,
`user_id` and `session_id` (the ids you pass to `run_async`), and its memory
service is what `add_session_to_memory` and the memory tools talk to. An
after-agent callback runs after every agent run, so this agent sends its session
to Memory Bank after every turn, and Memory Bank consolidates what it already
holds; to save once per conversation, call `add_session_to_memory` when your app
decides the conversation is over.

<Callout type="warning">Long-term memory is personal data. Keep only what the agent needs, scope it to the user, and set a time to live that matches your retention rules.</Callout>

## Choosing the place

- **Needed only for this turn?** `temp:` state.
- **Part of this conversation?** The session's events and plain state.
- **A setting your app owns, the same every time?** `user:` (or `app:`) state on
  a persistent session service that shares those scopes (verified on
  `DatabaseSessionService`). Your code writes and reads it exactly.
- **A fact users mention that you did not model as a field?** Memory Bank, which
  extracts it, consolidates it and recalls it when relevant.
- **Everything, pasted into the prompt?** Never. Every token in the prompt costs
  latency and money on every call, distracts the model and spreads personal data;
  topic 3.8 measures it.
