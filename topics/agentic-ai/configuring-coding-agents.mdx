## Context and tools decide what a coding agent can do

A coding agent is an agent whose job is software work: it reads your code,
runs commands, edits files and calls tools, in a loop, until the task is done.

That loop is what separates it from a chat assistant. A chat assistant answers
in text: it suggests code, and you copy it, run it and report back what broke.
A coding agent does those steps itself:

1. **Read** the code, tests and docs the task touches.
2. **Plan** the change.
3. **Change** the files.
4. **Verify**: run the tests, the linter or the build, read the result and go
   round again until the check passes.

Verification makes the biggest difference, because it is how the agent finds
its own mistakes, and the step a chat assistant leaves to you.

<Flashcard id="chat-vs-coding-agent" front="What does a coding agent do that a chat assistant does not?" back="It works the loop itself: it reads the code, plans the change, edits the files and verifies the result by running tests or a build, going round again until the check passes. A chat assistant only suggests code in text, and you run and check it." />

Two things decide how useful and how safe a coding agent is.

- **Context.** Without your team's conventions and procedures, the agent
  guesses. With them, it does the work your way.
- **Tools.** Without the right tools, it cannot reach your systems. With too
  many, it can do things the task never needed, some of them damaging.

Coding agents such as <Term id="antigravity">Antigravity</Term> (Google's
agentic development environment) and Claude Code (Anthropic's) handle both the
same way. An **<Term id="mcp server">MCP (Model Context Protocol) server</Term>**
gives the agent tools.
A **<Term id="skill">skill</Term>** gives it know-how. A project instructions
file (`AGENTS.md` or `GEMINI.md` in Antigravity, `CLAUDE.md` in Claude Code)
holds the few facts it needs on every task.

| You want the agent to | Use | Example |
|---|---|---|
| Call a live system | An MCP server | Look up a BigQuery table's schema |
| Follow a procedure for one kind of task | A skill | Review a query's cost with the team's checklist |
| Always know a short fact about the project | The instructions file | "Tests run with `npm test`" |

Antigravity has three main surfaces besides its editor integrations, and the
choice depends on who drives the agent and where:

| Surface | What it is | Choose it when |
|---|---|---|
| Antigravity App | The desktop application, where you hand tasks to agents and review their work | A developer works interactively on a project |
| Antigravity CLI (`agy`) | A terminal client that opens an interactive session in the current folder | You work in a terminal, or want the agent beside your other command-line tools |
| Antigravity SDK | A Python SDK (`pip install google-antigravity`) for building your own agents on Antigravity and Gemini | You are building a product or automation around the agent, not using it yourself |

Antigravity also offers a standalone Antigravity IDE and editor extensions (for
VS Code, JetBrains and others) for developers who want to stay in an editor.

## Add an MCP server, with only the tools the task needs

The **Model Context Protocol (<Term id="mcp">MCP</Term>)** is an open standard
for offering tools to agents. An MCP server publishes tools, each with a name,
a description and typed parameters; the coding agent is the client that lists
and calls them. Google Cloud runs remote
<Term id="google cloud mcp servers">MCP servers</Term> for its own services. The
one for BigQuery is at `https://bigquery.googleapis.com/mcp`, and its tools
include `list_dataset_ids`, `get_table_info`, `execute_sql_readonly` and
`execute_sql`, the one tool that can change data.

Say the team wants the agent to look up schemas while it writes queries. In
Antigravity, a workspace's MCP servers go in `.agents/mcp_config.json`, which
you can commit so the whole team gets them:

```json
{
  "mcpServers": {
    "bigquery": {
      "serverUrl": "https://bigquery.googleapis.com/mcp",
      "authProviderType": "google_credentials",
      "enabledTools": ["list_dataset_ids", "get_table_info", "execute_sql_readonly"]
    }
  }
}
```

- `serverUrl` points at a server over the web (Streamable HTTP, MCP's standard
  way to reach a remote server).
- `authProviderType: "google_credentials"` attaches your Application Default
  Credentials (ADC: the Google sign-in that
  `gcloud auth application-default login` saves on your machine, so tools can
  act as you).
- `enabledTools` is an allowlist: every other tool on the server, including
  `execute_sql`, is hidden from the agent.

In Claude Code, a project's MCP servers go in `.mcp.json` at the project root,
which you commit to share them, and Claude Code asks each developer to approve
them before first use. Google's MCP servers accept a bearer token, so a
`headersHelper` command can fetch one from each developer's own gcloud sign-in
every time Claude Code connects:

```json
{
  "mcpServers": {
    "bigquery": {
      "type": "http",
      "url": "https://bigquery.googleapis.com/mcp",
      "headersHelper": "gcp-mcp-headers"
    }
  }
}
```

Here `gcp-mcp-headers` is a short script you write and put on each developer's
`PATH`. It prints the request headers as JSON, with a token from the same
Application Default Credentials Antigravity uses:

```bash
#!/usr/bin/env bash
# gcp-mcp-headers: request headers for Google Cloud MCP servers
set -euo pipefail
token="$(gcloud auth application-default print-access-token)"
project="$(gcloud config get-value project 2>/dev/null)"
printf '{"Authorization": "Bearer %s", "x-goog-user-project": "%s"}\n' "$token" "$project"
```

To check the setup, run `claude mcp list`, which should show `bigquery` as
connected (approve it first by starting `claude` in the project), then ask the
agent for something read-only, such as listing the datasets in your project.
Claude Code has no allowlist field in this
file, so to keep a tool away from the agent, add a deny rule such as
`mcp__bigquery__execute_sql` to the permissions in Claude Code's settings; a
denied tool is removed from the agent's context.

The caller also needs permission on the Google Cloud side, through Identity and
Access Management (IAM), Google Cloud's system of roles and permissions: the MCP
Tool User role (`roles/mcp.toolUser`) to call a Google Cloud MCP server's tools,
plus the product's own roles, such as BigQuery Data Viewer and BigQuery Job
User. With only those two BigQuery roles, even `execute_sql` cannot change data.
Roles add up, though: a developer who also holds Editor or BigQuery Data Editor
can still change data through it.
Hiding a tool in the agent is a convenience; IAM is what the server enforces.

Expose the fewest tools the task needs. Every tool is a way in for an attacker:
the agent can call it by mistake, or because text it read in a file or web page
told it to. Every tool is also one more option the model has to weigh before it
picks the right one.

## Write a skill that loads only when relevant

A skill is a folder with a `SKILL.md` file. Its frontmatter (a short YAML
header between `---` lines, as in the example below) holds a `name` and a
`description`; its body holds the instructions. Antigravity reads
workspace skills from `.agents/skills/`, and Claude Code from `.claude/skills/`;
both follow the same `SKILL.md` format.

```text
bigquery-cost-review/
├── SKILL.md            # name, description, then the checklist
├── pricing-rules.md    # long reference, read only when the checklist says so
└── scripts/
    └── dry_run.sh      # runs a dry run and prints the bytes the query would scan
```

```markdown
---
name: bigquery-cost-review
description: Reviews a BigQuery query's cost before it ships. Use when the user asks for a cost review, or when a query reads a large table.
---

1. Run scripts/dry_run.sh on the query and report the bytes it would scan.
2. Check that the query reads only the columns and dates it needs.
3. If the scan is over 1 TB, apply the limits in pricing-rules.md.
...
```

The agent loads a skill in steps, which is called **<Term id="progressive disclosure">progressive disclosure</Term>**:

1. **Every turn:** the name and description of every skill (unless it is set
   to manual-only) are in the agent's
   <Term id="context window">context window</Term>, the text the model sees on
   each turn, so the agent knows what it could use.
2. **When a task matches the description**, or someone types `/bigquery-cost-review`,
   the agent reads the full `SKILL.md`.
3. **Only if the body points to them**, it reads the other files, such as
   `pricing-rules.md`. Scripts are meant to be run rather than read, so
   normally only their output enters the context.

so keep descriptions short), as long as each description says plainly what the
skill does and when to use it. A vague description is the
usual reason a good skill never gets used.

## Run the agent against your Google Cloud project

Enterprises want coding-agent traffic to run under their own cloud account,
terms, billing and controls. Both agents in this lesson can do that.

**Claude Code through Agent Platform.** Claude models are offered in Agent
Platform's Model Garden, so Claude Code can call them in your project instead
of Anthropic's API:

1. Enable the Agent Platform API: `gcloud services enable aiplatform.googleapis.com`.
2. Request access to the Claude models you want in Model Garden.
3. Give developers the `roles/aiplatform.user` role, which allows model calls.
   A dedicated project keeps cost tracking and access simple.
4. Point Claude Code at the project, with the login wizard (choose
   **Google Vertex AI**; Vertex AI is Agent Platform's former name, which Claude
   Code's settings still use) or with environment variables:

```bash
export CLAUDE_CODE_USE_VERTEX=1
export CLOUD_ML_REGION=global
export ANTHROPIC_VERTEX_PROJECT_ID=my-project
```

`CLOUD_ML_REGION` is the region that serves the model; `global` lets Google
choose, though some models need a regional endpoint, so check Model Garden.

Claude Code authenticates with standard Google credentials, such as Application
Default Credentials. For a team rollout, pin specific model versions in
Claude Code's settings, so everyone moves to a new model when you choose.

**Antigravity with a business account.** Developers sign in with a business
account and choose **Continue with Google Cloud**, then pick the Google Cloud
project linked to the company's licence. Sessions then run under the Google
Cloud Terms of Service, and model interactions are logged to that project. On
the enterprise tier Antigravity offers Gemini models and, if an administrator
opts in, Claude models.

<Callout type="note">Coding-agent products change quickly: file names, settings and model lists in this lesson are as documented in November 2026. The ideas (tools through MCP, know-how through skills, the fewest tools the task needs) carry over.</Callout>

## Recap

- An MCP server gives a coding agent tools; a skill gives it know-how; the
  project instructions file holds the few facts needed on every task.
- Expose only the tools the task needs: `enabledTools` in Antigravity, a deny
  rule in Claude Code, and IAM roles on the Google Cloud side, which is what the
  server enforces.
- A skill loads in steps: its name and description on every turn, `SKILL.md`
  when a task matches, other files only when the body points to them. A clear
  description is what gets it used.
- Claude Code runs through Agent Platform once the API, model access, the
  `roles/aiplatform.user` role and its Vertex settings are in place; Antigravity
  runs under your Google Cloud terms with a business-account sign-in.
