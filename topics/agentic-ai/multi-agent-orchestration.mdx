## More agents is not the goal

Splitting a task across several agents helps when the parts are distinct: each
agent gets a short instruction and only the tools it needs, independent parts
can run at once, and one part can check another. It hurts when the split adds
model calls, latency and places for results to get lost.

The question to answer first is: **do you know the order of the steps?**

- If you do, wire it up deterministically: the workflow runs the steps in the
  order you wrote, with no model deciding what comes next. That is cheaper,
  faster, testable and repeatable.
- If you do not, because the next step depends on what the user says, let a
  model route: a coordinator agent delegates to specialist sub-agents by their
  descriptions (topic 3.2).

A common failure is an LLM router in front of steps that always run in the same
order. Each request then pays for routing calls and sometimes takes the wrong
path.

## The patterns

All the agents in one run share the **session state**, a key-value store for
the conversation: one agent writes a key (in ADK, an `LlmAgent` with an
`output_key` saves its final response under that key) and later agents read it,
for example through a `{key}` placeholder in their instruction.

| Pattern | Shape | Use it when |
|---|---|---|
| <Term id="sequential agent">Sequential</Term> | A, then B, then C | Each step needs the previous step's result |
| <Term id="parallel agent">Parallel</Term> | A, B and C at once (a fan-out), then a join that waits for all of them | The steps are independent and latency matters |
| <Term id="loop agent">Loop</Term> | Repeat A and B until done or capped | Work improves by iteration, such as draft and review |
| <Term id="graph workflow">Graph</Term> | Nodes and edges, with routed branches, joins and back-edges | The paths are known but branch or loop |
| LLM-routed | A coordinator's model picks the next agent | The order cannot be known in advance |

### Graphs: branches and back-edges

A graph workflow is a set of **nodes** (agents or plain functions) joined by
**edges**. A plain edge always runs the next node. A **router** is a node whose
code returns a route name, such as `BUG` or `BILLING`, and a **routed edge** is
taken only when that name is returned, so one router can send work down
different branches. A **back-edge** is a routed edge that points to an earlier
node, which is how a graph loops: the router returns `RETRY` to go round again
and `DONE` to leave.

Sequential, parallel and loop are special cases of a graph. In ADK 2.0 you
express all of them as graph workflows; the older `SequentialAgent`, `ParallelAgent` and
`LoopAgent` classes still run in Python but are deprecated and scheduled for
removal.

## Run the refund task three ways

The simulation prepares a refund decision. An order agent loads the order; a
fraud check and a policy check assess it; a summary agent decides. Run it as a
sequential workflow, then as a parallel one, then try the parallel run with both
checks writing the **same** state key. Finally switch to a loop, where a writer
drafts the refund note and a reviewer approves or rejects it, and turn the
reviewer's ability to end the loop off.

<Simulation id="orchestration-patterns" height={900} />

What you should see:

- **Parallel is faster.** The two checks do not depend on each other, so running
  them at once cuts the run from 8 to 6 seconds.
- **A shared key loses a result.** When both checks write `check_result`, the
  policy check finishes first and the fraud check overwrites it a second later.
  The summary sees only "low risk", cannot confirm the return window and
  hands the refund to a person: the run finished faster, without the result it
  needed.
- **A loop without an exit runs to its cap.** With the reviewer unable to end
  the loop, the writer keeps drafting after approval until the cap stops it.
  With the exit on but a cap of 1 or 2, the loop stops before the note is
  approved.

## Parallel branches and shared state

Parallel branches run against the same session state. Two rules keep them safe:

1. **Each branch writes its own key**, such as `fraud_result` and
   `policy_result`, or returns its output to a join node, which passes the
   collected outputs to the next step keyed by the name of each node that feeds it.
2. **No branch reads a key another branch is writing.** If B needs A's result,
   B depends on A, and they belong in sequence.

Here is the refund workflow as an ADK 2.0 graph, with the two checks fanned out
and joined:

```python
from google.adk import Agent, Workflow
from google.adk.workflow import JoinNode

fraud_check = Agent(
    name="fraud_check",
    model="gemini-flash-latest",
    instruction="Assess the fraud risk of this refund: {order}",
    output_key="fraud_result",   # its own key
)
policy_check = Agent(
    name="policy_check",
    model="gemini-flash-latest",
    instruction="Check this refund against the 30-day return policy: {order}",
    output_key="policy_result",  # a different key
)
summary_agent = Agent(
    name="summary_agent",
    model="gemini-flash-latest",
    instruction="Decide on the refund. Fraud: {fraud_result}. Policy: {policy_result}.",
)

join_checks = JoinNode(name="join_checks")

root_agent = Workflow(
    name="refund_workflow",
    edges=[
        ("START", fraud_check, join_checks),
        ("START", policy_check, join_checks),
        (join_checks, summary_agent),
    ],
)
```

The two rows that start at `START` fan out, so the checks run at once;
`join_checks` waits for both before `summary_agent` runs. (Here the order is
assumed to be in state already as `order`.)

## Every loop needs an exit and a cap

A loop repeats work until it is good enough, such as a writer and a reviewer
taking turns. It needs two ways to stop:

- **An exit condition** for success. In a `LoopAgent`, a sub-agent ends the loop
  by escalating, which signals the parent workflow to stop: a tool sets `tool_context.actions.escalate = True`, and the
  built-in `exit_loop` tool does exactly that. In a graph, a router returns a
  `DONE` route instead of the back-edge's `RETRY` route.
- **A cap** for failure. In Python, a `LoopAgent`'s `max_iterations` defaults to
  none, so without an escalation it never stops on its own. A graph cycle is not
  bounded automatically either: count attempts in state and route out at the
  cap.

Here is the review loop as a graph, with both stops in the router. The router
accepts only an exact verdict: a substring test such as `"APPROVED" in
node_input` would also match "NOT APPROVED" and send a rejected note. Treat
anything that is not exactly `APPROVED`, including a malformed reply, as a
rejection.

```python
from google.adk import Context, Event, Workflow

MAX_ATTEMPTS = 3

# The reviewer's instruction says: reply with exactly APPROVED, or REJECTED: <reason>.
def review_router(ctx: Context, node_input: str):
    attempts = ctx.state.get("attempts", 0) + 1
    verdict = node_input.strip().upper()
    if verdict == "APPROVED":                  # exact match; anything else is a rejection
        return Event(route="DONE", state={"attempts": attempts})      # exit condition
    if attempts >= MAX_ATTEMPTS:
        return Event(route="GIVE_UP", state={"attempts": attempts})   # cap
    return Event(route="RETRY", state={"attempts": attempts})

root_agent = Workflow(
    name="refund_note_loop",
    edges=[
        ("START", draft_writer, reviewer, review_router),
        (review_router, {"RETRY": draft_writer, "DONE": send_note, "GIVE_UP": hand_to_person}),
    ],
)
```

ADK's run-level limit on model calls (`max_llm_calls` in the run configuration,
topic 3.1) is a last-resort backstop, not a loop design: by the time it fires,
the loop has already spent its budget.
