## Two kinds of agent, no code

<Term id="workflow builder">Workflow Builder</Term> is the low-code tool inside Gemini
Enterprise for building agents (it was called Agent Designer until it became
generally available in September 2026). It builds two kinds:

- A **chat agent** holds a conversation. The user drives: they ask, the agent works
  out how to answer, possibly with sub-agents for specialist tasks. Google describes
  its responses as mainly non-deterministic. It suits questions and answers, data
  lookup and personal help.
- A **workflow** runs a sequence of steps that you lay out on a canvas. Something
  starts it, the steps run in your order, conditions choose branches, and people can
  be asked to approve. It suits multi-step processes with a defined order and human
  sign-off.

In the terms of the first lesson in this path, a chat agent is an agent the user
leads, and a workflow is a workflow with model calls inside its steps. The test is
the same: if the path should be fixed and checked, build a workflow; if the user
should lead an open conversation, build a chat agent.

Both reach business apps through **connectors**: Gemini Enterprise's links to apps
such as Gmail, Google Drive, Jira and ServiceNow, connected to the Gemini
Enterprise app as data stores.

## One request, built twice

Take a new-starter request. A manager emails HR: "Maria joins on 3 March as a
support engineer, please set her up."

**As a chat agent**, you give the agent instructions ("help managers onboard new
starters: collect the name, role, start date and manager, then raise the IT
ticket"), and it works with the handbook and the apps connected to your Gemini
Enterprise app. The manager opens it in Gemini Enterprise and talks it through. It is
flexible and copes with odd requests, but it decides its own steps each time, so
nothing guarantees the same checks happen for every new starter, or that the
details are reviewed as a whole before anything is created.

**As a workflow**, the request starts the process itself and every request goes
through the same steps:

Step through the canvas below. First predict what happens when the request names no
manager, then follow the condition down both of its branches.

<Simulation id="workflow-canvas-flow" />

1. **Trigger.** An event trigger watches Gmail for received emails, filtered to the
   new-starter subject line.
2. **Gemini Agent step.** Its instructions say to extract the name, role, start date
   and manager. Its knowledge is the onboarding handbook. Its output format is a
   **JSON schema**, a list of named fields the output must fill, here those four.
   Each field becomes a **variable**: a named value later steps can read.
3. **Condition.** If the manager field is empty, a separate branch replies to the
   sender asking for one (a connector write, so it needs review too), and that run
   ends.
4. **Approval.** The run pauses and a reviewer checks the extracted details as a
   whole.
5. **Gemini Agent step with connector actions.** It creates the IT ticket and sends
   the welcome email.

What the workflow guarantees, and the chat agent doesn't: every request is handled
the same way, the details are checked against a schema, and nothing is created
until a person has approved the request as a whole.

## Configuring a workflow

### Triggers

A <Term id="trigger">trigger</Term> starts a workflow, in one of three ways:

- **Manual:** someone types @ and the workflow's name in the Gemini Enterprise chat,
  and can be asked for input fields.
- **Schedule:** a frequency (such as daily or weekly) and a time zone. Scheduled runs
  that affect other people, such as sending email, pause for approval in the chat.
- **Event:** a change in a connected app: a new email in Gmail, for example, or a
  change in Google Calendar, Google Drive, ServiceNow or Jira Cloud.

An event trigger is configured as the workflow's trigger, not added as a step on
the canvas: choose
**App event**, then the connector, then its event, then filters. Google's advice is
to always add filters, so that only the emails or files you mean start runs. Event
triggers work by **polling**, checking the app at intervals, so a run can start 5 to
10 minutes after the change. They only poll while the workflow is turned on.

<Flashcard id="event-trigger-inline" objective="configure-workflow" front="An event trigger fired 8 minutes after the email arrived. Is something wrong?" back="Probably not. Event triggers poll the connected app, and Google documents a delay of 5 to 10 minutes." />

### Steps

- **<Term id="gemini agent step">Gemini Agent step</Term>.** A model acts on
  **instructions**, **knowledge** (files, or chosen Drive or OneDrive folders) and
  **connected apps**. For each connector you turn on search actions, and separately
  the actions that add or update data. Write actions need the search actions too,
  because they find the record to change by searching first; without them the run
  fails with an ENTITY_NOT_FOUND error. Adding or updating data through a connector
  also requires human review of that write. The **output format** is plain text or a
  JSON schema, and the output becomes a variable. A JSON field gives later steps an
  exact value to test; free text can be worded many ways.
- **Flow control.** **Condition** branches on a variable (equals, contains, greater
  than, joined with AND or OR). **Filter** keeps only the list items that match.
  **Loop** runs one or more steps for each item in a list.
- **Human in the loop.** **Request info** pauses to ask a person questions that you
  set when you build the step (short answer, date, yes or no and others).
  **Approval** pauses until a person signs off on what the workflow has produced so
  far.
- **Steps that reach outside.** MCP steps call tools on an MCP server, and
  existing-agent steps run registered ADK or A2A agents built outside Workflow
  Builder. A later
  lesson covers when to use them.

<Callout type="warning">Put the approval step before the first step that is hard to undo: sending a message, creating an account, changing a record or moving money. An approval after that step only reviews what has already happened. It also does a different job from the review that connector writes require: the approval looks at the whole request once, before the actions start.</Callout>

### Building by conversation

You can also describe a workflow, or a change to one, in plain language and let the
designer build it. At the time of writing, Google lists a known issue: it can't add
approvals, event triggers or filters this way, so add those by hand.

## Operating a workflow

### Versions

When a workflow is ready, you **turn it on**. That version becomes **Live**, and a
new draft is created for your next edits, so changes never touch the running
version until you update it. You can also save a version without making it live.
Before turning a draft on, try it from the **Preview** tab, which runs it as a test
without waiting for the trigger; for an event trigger, you pick a recent event as
the sample input.

Version history lists each version with its name and time. Restoring one copies it
over the current draft, which you then make live with **Update**. Deleting a version
can't be undone, doesn't make any other version live, and removes the workflow
graph from that version's runs, so you lose the graph those runs are debugged
against.

Turning a workflow off removes its schedules and event triggers, so no new runs
start, for everyone it is shared with. Runs already under way finish.

### Run logs

The **Runs** tab lists every run of the workflow, both the test runs started from
Preview and the real runs from its trigger. Each run shows its input or trigger, its
status and when it started. Statuses include **Running**, **Needs Review** (paused
at a human-in-the-loop step), **Completed** and **Error**, and you can filter by
them and by date. Opening a run shows its details, including which version ran, and
Google describes the logs as step-by-step execution traces.

So to debug, find the failed run, see which step failed and with what message, fix
that step in the draft, test it in Preview, then update the live version. One
caution from the known issues: event-triggered runs that fail because a quota ran
out are not retried automatically.

## Try it

If your organisation's Gemini Enterprise has Workflow Builder turned on, build the
new-starter workflow above with a filter on your own test subject line and a test
ServiceNow instance or test inbox, since a test run may perform real actions. Send
yourself a test email, then in the Preview tab (some pages call it Test) choose
it with Select input and click Start manually. Then turn it on, send another email, and follow the run in the Runs tab,
including the pause at the approval.
