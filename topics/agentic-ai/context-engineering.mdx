## Context is a budget

Every model call an agent makes carries a **<Term id="context window">context</Term>**: everything the
model sees in that one call. At low traffic you can ignore it. At scale, it
decides three things:

- **Cost.** Input tokens are billed on every call, and an agent makes several
  calls per turn.
- **Latency.** More tokens take longer to process before the first output token.
- **Quality.** Material the model does not need still competes for its
  attention: an extra tool is one more wrong choice, an old turn is one more
  thing to misread.

So treat context as a budget, and spend it on what the current step needs.

## Break a turn into its parts

On each call an ADK agent sends the model these parts, in roughly this order:
the parts that stay the same on every call first, then the parts that change.

| Component | What it is | Grows with |
|---|---|---|
| Instructions | The agent's instruction (system prompt) | Fixed per agent (except values filled in from session state, covered below) |
| Tool declarations | Name, description and parameters of every tool the agent can call | Number of tools |
| History | Earlier turns, including tool calls and tool results | Every turn |
| Memory | Facts recalled from past sessions | How memory is recalled |
| Retrieved content | Chunks of documents fetched from a knowledge base | Number of chunks and their size |
| User message | The new input | Message length |

To find the largest part, measure it. Each model response carries **usage
metadata**, a set of token counts for that call, including the prompt's total.
The Gemini API's `count_tokens` call counts any piece on its own, such as the
instructions, the declarations or the retrieved chunks. Measure on real long
sessions, because history is small at turn 2 and dominant at turn 20.

Take a support agent at ten times its launch traffic. Two MCP servers have been
connected (MCP, the Model Context Protocol, is the standard way to plug a
server's ready-made tools into an agent), so it now has 40 tools, and its
conversations run long. A turn late in a long session looks like this
(illustrative numbers):

- instructions 3,000 tokens
- tool declarations 10,000 (40 tools at about 250 each)
- history 18,000
- preloaded memory 6,000
- retrieved chunks 10,000 (ten chunks of about 1,000 tokens)

That is 47,000 tokens before the user's message, and history is the largest
part.

### Tool declarations: expose only what the step needs

Every declaration is in front of the model on every call, so 40 tools mean 40
candidates for each choice, many with similar names, and about 10,000 tokens
of declarations. Give each agent, or each step, only the tools it needs:

- **Filter a toolset.** An ADK `McpToolset` connects to one MCP server and
  exposes its tools to the agent. It takes a `tool_filter` list, and ADK's
  security and scoping guidance is to always supply one, so the model sees only
  the necessary actions.
- **Split by task.** A coordinator delegates to sub-agents (topic 3.2), each
  with a short instruction and the handful of tools its task needs.

```python
from google.adk.tools.mcp_tool import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StreamableHTTPConnectionParams

orders_tools = McpToolset(
    connection_params=StreamableHTTPConnectionParams(url=ORDERS_MCP_URL),
    tool_filter=["get_order", "get_refund_status", "check_warranty"],
)
```

With the other server filtered the same way, the agent sees 8 tools instead of
40, and the declarations drop to about 2,000 tokens. A model with a larger
context window does not help here: it fits all 40 declarations, and all 40
choices are still in front of the model.

### History: compact it

ADK records a session as **events**: each user message, model reply, tool call
and tool result is one event, and one user turn with everything it triggers is
one **invocation**. <Term id="history compaction">History compaction</Term>
summarises older events and keeps the most recent ones as they were. In ADK
you set an `EventsCompactionConfig` on the `App`, ADK's top-level object that wraps the root agent together with app-wide settings such as compaction and caching, and the runner compacts the
session's events for you. Token-based compaction triggers once a model call's
prompt reaches a threshold, and keeps the last few events raw; a sliding window
instead compacts every few invocations.

```python
from google.adk.apps.app import App, EventsCompactionConfig

app = App(
    name="support_app",
    root_agent=root_agent,
    events_compaction_config=EventsCompactionConfig(
        token_threshold=30000,    # compact once a call's whole prompt reaches this
        event_retention_size=5,   # keep the 5 most recent events as they were
    ),
)
```

The threshold counts the whole prompt, so set it above the fixed part
(instructions, tools, memory and retrieval), or every call compacts. Pass the
App to the runner, `Runner(app=app, session_service=...)`; compaction runs only
through the App.

A summary can drop a detail. Facts the agent will need again, such as an order
id, belong in **session state**: key-value pairs stored on the session for the
whole conversation, which compaction does not summarise (topic 3.3 covers state
in full). A tool writes a key, for example
`tool_context.state["order_id"] = order_id`, and an optional placeholder such as
`{order_id?}` in the agent's instruction puts the value back in front of the
model on every call. The `?` makes it render empty until the key is set. Put
placeholders at the end of the instruction, so the fixed text before them stays
the same on every call. With ADK's explicit caching (below), a change to a
placeholder's value means a new cache wherever the placeholder sits.

### Memory: recall it on demand

Long-term memory is a store, searchable across sessions, that ADK's memory
service fills from past conversations. It is separate from session state, which
lasts for one session. ADK offers two ways to bring memory into a turn. The
`preload_memory` tool searches memory with the turn's user message before
every model call and adds the results, so what it adds changes from turn to
turn. The `load_memory` tool lets the model search memory only when it
judges a turn needs it. If most turns are about the current order, preloading
spends memory tokens on every call for nothing; `load_memory` fetches them only
on the turns that ask.

Fetching less often is not the whole story. Preloaded memory is added to each
call and not kept, but a `load_memory` result is an ordinary tool result, so it
stays in the history and rides along on later calls until compaction
summarises it. Count both the newly fetched tokens and the recalled tokens
still in history, and measure prompt totals over several turns rather than
inferring them from how often the tool is called. In the example, assume one
turn in four recalls memory and compaction summarises each recall within a
turn or so: memory then costs about 1,500 tokens per late turn instead of
6,000. That is an assumption to check with measurements, not a rule.

### Retrieved content: pass fewer, better chunks

Retrieval splits documents into chunks, finds the k chunks that best match the
query (the **top-k**), and adds them to every call that answers from retrieved
content. A **reranker** rescores those candidates for relevance so you can pass
fewer of them. Reranking plus a smaller top-k (topic 3.4 goes deeper) usually
keeps the right evidence in fewer tokens. Retrieve only on the steps that need
it.

### Images, video and PDFs: send by reference, cap the tokens

Media raises two separate problems, with two separate fixes.

- **Payload size and reuse.** Inline bytes travel inside every request that
  carries them, and requests have a size limit (the Gemini API documents 100 MB
  per request inline, 50 MB for PDFs; check your endpoint's limit). For a large
  file, or one used on many calls, pass a **Cloud Storage URI** (`gs://...`)
  instead: Agent Platform accepts one directly, and the Gemini Developer API
  takes it once registered through its Files API. The request then carries a
  reference, and the bytes are not uploaded again on each call.
- **Tokens.** A referenced file still costs tokens every time it is in the
  context. The `media_resolution` setting caps how many tokens each image,
  video frame or PDF page may use. For Gemini 3 and later images, `low` is 280 tokens,
  `medium` 560, `high` 1,120 (also the default) and `ultra_high` 2,240.
  Video frames use 70 tokens at low or medium and 280 at high. Lower it when
  the task does not need fine detail, such as classifying a photo, and raise it
  for small text in a scanned document.

## Context caching: cheaper, not smaller

The model reads a request from front to back. The parts that are the same on
every call (instructions and tool declarations) form its front, or
**prefix**; history, memory, retrieved chunks and the new message come after it.

**<Term id="context caching">Context caching</Term>** reuses the processing
of a prefix that repeats across calls. It cuts the cost and latency of that
prefix. It does not cut the context: the cached tokens still form part of the input
context, still count in the context window, and are still in front of the model.

- **Implicit caching** is on by default for Gemini 2.5 and newer models. It
  applies when a request's prefix matches an earlier one and is above a
  model-specific minimum (2,048 tokens on Gemini 2.5 models, 4,096 on several
  newer ones). Put large, common content at the start of the prompt and
  changing content, such as the date, after it.
- **ADK's context caching** is configured on the `App` with a
  `ContextCacheConfig` (`min_tokens`, `ttl_seconds`, `cache_intervals`). ADK
  then creates and refreshes cache entries itself, with a lifetime and a reuse
  count you set, instead of relying on automatic matching. The class is
  experimental, and explicit caches are not available on every model.
- The response's usage metadata reports how many tokens came from the cache
  (`cached_content_token_count` in the Gemini API's `usage_metadata`), so check
  that count, not the input total.

On the published price lists, cached input tokens bill at a fraction of the
standard input rate (for Gemini 3.5 Flash, a tenth). Explicit caches, such as
those ADK's `ContextCacheConfig` creates, also bill storage for each hour they
live. Rates vary by model, so check the current pricing page for yours.

Caching pairs with the cuts above: it makes a lean, stable prefix cheap. It is
not a substitute for them.

## Prove every change with an evalset

A context change can save tokens and quietly break an answer: a filter drops a
tool a rare request needs, or a summary drops a detail. Token counts show the
saving; only evaluation shows the cost.

An <Term id="evalset">evalset</Term> is a fixed set of cases. Each case is a
conversation that records the user's input, the tool calls you expect (with
arguments) and a reference reply. ADK runs the agent on every case and scores
it:

- `tool_trajectory_avg_score` checks that the agent made the expected tool
  calls. Default threshold 1.0, an exact match.
- `response_match_score` checks how close the reply is to the reference.
  Default threshold 0.8.

Each criterion scores a case from 0 to 1, averaged over its turns, and a case
passes when its score reaches the threshold.

The same run also reports efficiency values that never pass or fail a case.
One of them, `token_usage_v1`, gives the average tokens per invocation, with a
breakdown that includes input, cached and output tokens. So one run measures
both the quality and the saving. Topics 4.2 and 4.4 go deeper.

The loop for each change:

1. Run the evalset on the current agent and record the scores and
   `token_usage_v1`.
2. Make one change, such as the tool filter.
3. Run the same evalset again with `adk eval`.
4. Ship only if the scores hold and the tokens fell. If a score drops, look at
   which cases failed: they usually share a cause, such as a missing tool.

stores the id in session state; before it, the id survives only if the

## Recap

- Context is a per-call budget: it drives cost, latency and quality.
- Measure tokens by component on long sessions, and cut the largest first.
- Filter tools, compact history (keep needed facts in state), recall memory on
  demand, and pass fewer, better chunks.
- Caching makes a stable prefix cheaper; it does not make the context smaller.
- Run the same evalset before and after each change, one change at a time.
