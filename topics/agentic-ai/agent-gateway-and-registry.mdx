## One agent is easy; fifty are not

With one agent, you can read its code to see which tools it calls. With fifty
agents, built by different teams, calling MCP servers, internal endpoints and
each other, nobody can. Two questions become hard to answer: **what is allowed
to exist**, and **what is actually happening**.

The last lesson answered **who is calling**: each agent has its own identity
and narrow roles. This lesson adds the other two pieces of runtime governance.

## Agent Registry: what exists

<Term id="agent registry">Agent Registry</Term> assigns distinct identifiers and
identities to registered agents, MCP servers, endpoints and skills, so that you
can **discover** capabilities, **enforce** access policies and **route** runtime
traffic. It is the catalogue the rest of governance refers to.

Each entry has two kinds of identifier, for two jobs:

- A **registry URN**, such as `urn:agent:…` or `urn:mcp:…`, for discovery and
  search. A team looking for an existing invoice agent searches the registry
  before building a new one.
- A **resource name**, such as `projects/…/locations/…/agents/…`, for
  governance. Policy bindings and gateway route rules use resource names. The
  registry's documentation is explicit: registry URNs cannot be used in IAM
  policy bindings, authorisation headers or gateway route rules.

Registered agents on Google Cloud also get a managed workload identity in SPIFFE
format: the agent identity from the last lesson. Agents outside Google Cloud
use Workload Identity Federation or a service account.

## Agent Gateway: what may happen now

<Term id="agent gateway">Agent Gateway</Term> is where policy on agent traffic
is enforced and observed. It sits on the traffic between agents and the tools,
MCP servers and other agents they call, and centralises access policies, mTLS
and MCP security. For each call it can:

1. **Know the caller**, from the agent's identity.
2. **Apply access policy**: is this target approved in the registry, and may
   this agent call it? Policies name targets by their resource names.
3. **Screen the content**, by configuring Model Armor on the gateway. The next
   lesson covers Model Armor itself.
4. **Record what happened**, as traces and access logs in Cloud Logging and
   Cloud Trace.

Because it is on the path, the gateway gives you one place to enforce rules and
one place to see every call, instead of trusting each team to build both into
each agent.

## Putting the three together

| Piece | Question | In the invoice example |
|---|---|---|
| **Agent identity** | Who is calling? | The invoice agent's own principal |
| **Agent Registry** | What exists, and is it approved? | finance-mcp is registered; pdf-tools-online is not |
| **Agent Gateway** | May this call happen now, and what happened? | The call to finance-mcp passes and is logged; the call to pdf-tools-online is refused and logged |

Design governance in that order. Give every agent its own identity. Register
every agent, MCP server and endpoint you approve. Then route agent traffic
through the gateway with policies that name the caller's identity and the
target's resource name. An unreviewed MCP server is then not just discouraged:
the call to it fails, and the attempt is on record.

## Recap

- Identity answers who is calling, the registry what exists, and the gateway
  whether a call may happen now, and what happened.
- Agent Registry catalogues agents, MCP servers, endpoints and skills. Use URNs
  for discovery and resource names in policies and route rules.
- Agent Gateway enforces access policies on agent traffic, can screen it with
  Model Armor, and records traces and access logs, in one place.
