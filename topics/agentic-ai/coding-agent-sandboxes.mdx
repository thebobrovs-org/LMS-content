## Agent-generated code is untrusted code

A coding agent writes code and runs commands. Both can be wrong: the model can
misread the task, or follow an
<Term id="indirect prompt injection">instruction hidden in a file or web page</Term>
it read. Whatever runs, runs with the permissions of the process and the
credentials around it. On a developer laptop that can mean SSH keys, cloud
credentials with production access, and every file in the home folder.

Three rules follow:

1. **Treat agent-generated code as untrusted** until it is reviewed and tested.
2. **Isolate where it runs**, and keep production credentials out of reach.
3. **Keep a person reviewing** every patch that ships.

The options below, summarised as a ladder in the figure further down, differ in what
they protect, and from what. Topic 2.2's hooks
and tool lists limit what an agent tries; isolation limits the damage when
something gets through.

## Antigravity's terminal sandbox and permission presets

Antigravity runs the agent's shell commands in a
<Term id="terminal sandbox">terminal sandbox</Term>, using each operating
system's built-in process isolation (kernel namespaces on Linux, Seatbelt on
macOS, AppContainer on recent Windows 11). It runs on the developer's own
machine, not in a Google-managed environment: there is no virtual machine or
container image, just a boundary around each command on the laptop. Inside it, writes are limited to the
workspace, temporary folders, build caches and paths you allow with
`write_file`, `~/.ssh` and `.env` files are blocked, and "sandboxed commands run
without network access by default". Domains you allow for `read_url`
(Antigravity's web-fetch permission) form the sandbox's outbound allowlist.

How much the agent may do without asking is set by a
<Term id="permission preset">permission preset</Term>:

| Preset | Sandbox | Terminal commands |
|---|---|---|
| Request Review | Off | Always ask |
| Default | On | Allowed in the sandbox; ask outside it |
| Auto | On | Allowed in the sandbox; outside it, Antigravity decides automatically instead of asking |
| Turbo | Off | Allowed, unrestricted, with full file system access |

Default is selected unless the sandbox is unavailable, in which case Antigravity
uses Request Review. Auto is not available for business or enterprise accounts,
and Turbo should never be used on a machine that holds production credentials.

On top of a preset, rules say what is allowed, what asks and what is denied,
written as an action and a target, such as `command(git push)` or
`read_url(registry.npmjs.org)`. When rules conflict, deny beats ask, and ask
beats allow. A team can combine them like this:

| Rule | Example | Effect |
|---|---|---|
| Allow | `command(npm test)` | Tests run without asking |
| Ask | `command(git push)` | Every push waits for approval, whatever else is allowed |
| Deny | `command(rm -rf)` | Commands starting `rm -rf` never run, even if a broader rule allows them |

Command rules match by literal prefix, so `rm -fr` is not caught: deny rules
narrow risk, but they are not a complete blocklist.

Two details catch teams out:

- **The CLI differs from the app.** In the Antigravity CLI the sandbox is off
  by default. Turn it on with `"enableTerminalSandbox": true` in its settings,
  or `agy --sandbox` for a session, and set `"toolPermission":
  "proceed-in-sandbox"` to let sandboxed commands run without asking.
- **Business and enterprise accounts use the earlier settings**,
  whose presets have different meanings: even their Default, like Full machine
  and Turbo mode, leaves the sandbox off.
  There, switch on **Enable Sandbox Mode** explicitly. Antigravity's enterprise
  guidance is to keep Default or Request Review enabled; its documentation does
  not describe an administrator lock on presets.

The sandbox confines commands, not credentials. A tool the terminal sandbox does
not cover, such as an <Term id="mcp server">MCP server</Term>, still acts with
whatever access it was given.

## Cloud Workstations: a managed machine per developer

<Term id="cloud workstations">Cloud Workstations</Term> moves the developer's
environment, and the coding agent with it, off the laptop. Each workstation
runs on its own VM inside your VPC. Google's security guidance is to disable
public IP addresses, put workstations in a VPC Service Controls perimeter (a
boundary that stops data in Google APIs such as Cloud Storage or BigQuery being
reached from, or copied to, projects outside it), and keep each workstation
single-user.

For coding agents, Google documents an agent-optimised setup: a workstation can
suspend when idle and keep its memory, processes and terminal sessions, and
sample hooks for Claude Code and Antigravity CLI keep it awake while the agent
is working.

The agent acts with the workstation's credentials: the service account attached
to its VM (the project's default workstation service account if you attach
none), plus any gcloud credentials a user saves there. Attach a dedicated
service account with only the roles development needs, and keep production
roles off it.

When an agent keeps hitting permission errors, resist granting Owner or Editor
so it "never fails". These basic roles turn every mistake or injected
instruction into a project-wide change. Give the agent its own identity, add the
one role a failing task shows it needs, and never lend it a developer's
credentials. Topic 5.2 covers agent identities and why basic roles are a trap.

## GKE Agent Sandbox: isolating generated code at scale

When an agent product runs code that agents generate for many users,
<Term id="gke agent sandbox">GKE Agent Sandbox</Term> gives each run its own
isolated environment. It was announced as generally available in May 2026 and
builds on the open-source Agent Sandbox project. This section assumes basic
GKE: a Pod is the smallest unit GKE schedules, and a network policy controls
which traffic may reach or leave it.

- **Isolation.** Each sandbox is a Pod with its own kernel boundary: GKE
  Sandbox with gVisor (a user-space kernel that intercepts the Pod's system
  calls) or with a microVM (a lightweight VM with its own guest kernel). Code
  that escapes its process must break a second boundary before it reaches the
  node or other tenants.
- **Resources.** A `SandboxTemplate` defines the Pod, a `SandboxWarmPool` keeps
  sandboxes ready "in less than one second", and a `SandboxClaim` takes one
  from the pool. A Python SDK creates the claims for you.
- **Network.** Pods created from a template get a default-deny network policy:
  no ingress except through the sandbox router (the component that forwards
  requests to a claimed sandbox), and no egress to private ranges, cluster DNS
  or the metadata server (the endpoint that hands out the node's credentials to
  anything that asks). **Public internet egress is
  allowed by default**, so restrict it if the code should not call out. A
  Sandbox you create directly, without a template, gets no network policy.
- **Operations.** You install the Agent Sandbox controller on your cluster and
  upgrade it yourself; it is not a managed add-on. It runs on Autopilot clusters (Google manages the
  nodes) and Standard clusters (you manage them).

Keep cloud credentials out of the sandbox too: Google's quickstart turns off
the automatic Kubernetes service-account token (the credential Kubernetes
mounts into every Pod by default), and with the template's network
policy blocking the metadata server, generated code cannot borrow the node's
identity.

<Callout type="note">For architects comparing options: Google's documentation now suggests a newer project, Agent Substrate on GKE, for most agent workloads, because it packs more agents onto the same nodes. It is open source, needs GKE Standard, and shows no launch stage in its documentation; GKE Agent Sandbox remains the documented choice for a dedicated Pod per agent, GPUs or Autopilot.</Callout>

## Choose isolation by scenario

| Scenario | Isolation | Keep out |
|---|---|---|
| One developer using a coding agent on a laptop | Terminal sandbox with the Default preset, or Request Review where the sandbox is unavailable | Production credentials on the laptop |
| An enterprise team of developers using coding agents | Cloud Workstations with no public IP, a perimeter and a minimal service account | Company credentials on laptops; production roles on the workstation |
| An agent product running generated code for many users | GKE Agent Sandbox, a sandbox per run from a warm pool, with egress restricted | Cloud credentials and the metadata server inside sandboxes |

## Patch a vulnerability with review gates

Isolation decides where agent code runs. Review decides what ships. Say a
scanner flags a vulnerable dependency, and a coding agent on a workstation
takes the task:

1. **Work on a branch, from a reproduction.** Where the flaw can be shown, the
   agent first writes a test that reproduces it and fails. Then it upgrades the
   dependency and fixes what the upgrade breaks, on its own branch, with
   permissions that cannot push to main, until that test passes.
2. **Test in isolation.** It runs the test suite inside the Antigravity CLI's
   terminal sandbox, turned on with `enableTerminalSandbox` (check that it
   starts: it needs unprivileged user namespaces, which some containers block),
   with only the package registry allowed. A malicious build script then cannot
   reach `~/.ssh` or `.env` files or call anywhere else. Save no gcloud
   credentials on the workstation, and its minimal service account limits the
   rest.
3. **Open a pull request.** CI, not the agent, runs the full tests and security
   scans; the agent cannot mark its own work as passing.
4. **A person reviews and merges.** The reviewer checks the diff, especially
   anything beyond the dependency bump, such as changed tests, new network
   calls or edited CI files.

The same gates apply to every maintenance job: the agent proposes, tests and
scans check, and a person decides. Protect the main branch on the server, so no
agent credential can skip the gates. What changes from job to job is the check
that proves the work is done:

| Job | The check | What it proves |
|---|---|---|
| Patch a bug or vulnerability | A reproduction test first: it fails before the fix and passes after | The fix addresses the actual flaw, not a guess at it |
| Refactor | The existing tests pass before and after, unchanged | Behaviour stayed the same; edited tests are a reason to look closer |
| Optimise, such as a JVM heap size or a Cloud Run concurrency limit | Measure, change, then measure again under the same load | The change helped; without a baseline, "faster" is a guess |

## Recap

- Agent-generated code is untrusted until reviewed and tested; isolate where it
  runs and keep production credentials out.
- Antigravity's terminal sandbox confines commands on the developer's own machine, with no network
  by default; presets decide what runs without asking, and rules resolve deny
  before ask before allow, so an ask rule guards risky commands such as a push. The CLI's sandbox is off until you turn it on.
- Cloud Workstations gives each developer a managed VM in your VPC; its service
  account is what the agent can do, so keep it minimal and never reach for
  Owner or Editor.
- GKE Agent Sandbox gives each run of generated code a kernel-isolated Pod from
  a warm pool; for Pods from a template it blocks internal traffic and the
  metadata server, but allows public egress unless you restrict it.
- Ship agent patches through a branch, CI tests and scans, and human review,
  with the main branch protected. Prove a patch with a reproduction test, a
  refactor with unchanged tests passing before and after, and an optimisation
  by measuring before and after.
