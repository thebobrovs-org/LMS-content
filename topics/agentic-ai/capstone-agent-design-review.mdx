The exam asks you to combine choices, not recite them. In this lesson you
design one agent from a written brief, one decision at a time, and tie each
decision to a line of that brief. Then you review a weaker design of the same
agent and name what is wrong with it. That is a
<Term id="design review">design review</Term>: a check of a design against its
requirements and the failure modes you already know.

Two rules run through everything below. **Every choice traces to a requirement.**
If you cannot point at the line in the brief that a choice serves, it is
decoration or a guess. **Evaluation, identity and guardrails are designed in
from the start.** Bolted on at the end, they cost a rebuild, which is the lesson
of the low-code-or-code topic.

## The brief

Northwind Outdoor, an online retailer, wants an agent on its website that
answers customers. The requirements, numbered so the design can cite them:

- **R1.** Answer questions about returns, shipping and warranty from about 2,000
  policy pages. The support team edits them every week.
- **R2.** Tell a signed-in customer the status of their own orders, which are in a
  Cloud SQL database. Never another customer's.
- **R3.** Issue refunds through the internal payments API. A refund over $200
  needs a support lead's approval first.
- **R4.** Customers sometimes paste card numbers into the chat. They must not be
  repeated or stored in logs.
- **R5.** The engineering team ships weekly and wants every change tested
  automatically before it reaches customers.
- **R6.** Traffic is quiet at night and ten times normal on sale days.
- **R7.** The security team must see and control which systems the agent can
  reach.
- **R8.** Keep what the team builds and operates, and the running cost, as low
  as the other requirements allow.

## Design it in ten decisions

Each step names the choice, the requirement behind it, and the lesson that
taught the reasoning.

<Steps>
<Step id="capstone-build-approach" title="Build approach: ADK, in code">

R5 asks for evaluation gated on every change, R3 needs a refund rule enforced
in code, and R2 needs a custom integration with the orders database. Those are
the signals for code from the low-code-or-code lesson, so the agent is built
with ADK. CX Agent Studio, Google's tool for customer conversations, is where
you would start if a contact-centre team owned the agent and most of it were
instructions and fixed flows. Here engineers own it and need that control.

</Step>
<Step id="capstone-model" title="Model: a managed Gemini model">

R8 favours the least to operate, and nothing in the brief asks to hold weights,
run the model on your own infrastructure, or cut cost at a measured, steady
volume, so the agent calls a managed Gemini model through the API. Start with one capable model, measure,
and only then route simple steps, such as classifying the request, to a
smaller one.

</Step>
<Step id="capstone-knowledge" title="Knowledge: Agent Search over the policy pages">

R1 is plain document question answering with no special pipeline needs, so the
first choice is Agent Search, Google's out-of-the-box RAG. The pages change
weekly, so the data store is kept in step with the source. Superseded pages are
marked with metadata and filtered out, because an outdated page is a data
problem, not a prompt problem. Reach for RAG Engine only when you need to
configure chunking, embeddings or reranking yourself.

</Step>
<Step id="capstone-tools" title="Tools: one safe query, one refund function">

For R2, the orders database is reached through MCP Toolbox for Databases with
one named, parameterised query, `get_orders_for_customer`, never a free-form
SQL tool. Its customer id comes from session state that the web app writes when
the customer signs in, not from the model: the agent wraps the Toolbox tool so
the wrapper reads the id from state and binds it, and the model never sees that
parameter. The MCP lesson's authenticated parameters fill such a value from a
verified Google sign-in token; these customers sign in to the website, not to
Google, so the binding is done in the agent's code. For R3, `issue_refund` is a function
tool that calls the payments API.

</Step>
<Step id="capstone-orchestration" title="Orchestration: one agent, no team">

One `LlmAgent` with three tools covers the brief: search the policies, look up
orders, refund. No step needs a specialist with its own instructions, and no
work runs in parallel. Use the least autonomy that solves the task: under R8, a
multi-agent design would add routing failures and cost without serving a
requirement.

</Step>
<Step id="capstone-sessions" title="Sessions and memory: persistent sessions, no Memory Bank">

A refund conversation can span several turns, and under R6 instances come and
go, so sessions must live in a persistent session service, never in instance
memory. The signed-in customer's id is held in session state. Nothing in the
brief asks the agent to remember facts across conversations, so there is no
Memory Bank.

</Step>
<Step id="capstone-evaluation" title="Evaluation: a golden evalset gated in CI">

For R5, an evalset records the expected tool calls as well as the answer. It
includes edge cases (a refund of exactly $200), adversarial ones (a pasted
instruction to refund someone else's order) and cases for R4. Trajectory
matching with `IN_ORDER` checks that the expected lookup comes before the
expected refund, while allowing extra calls. An extra, unexpected refund would
still pass, so the adversarial cases also assert that no refund happens. CI runs the evalset on every change
and fails the build on a regression. After launch, sampled live traffic is
scored with reference-free checks, and every failure found becomes a new case.

</Step>
<Step id="capstone-runtime" title="Runtime: Agent Runtime">

R6 asks for scale, and R8 for no idle machines to run. Agent Runtime is the managed
option with sessions, evaluation and observability services alongside. It
gives the least to operate while still meeting the brief. Cloud Run would also
work, with the session service configured by you.

</Step>
<Step id="capstone-identity-auth" title="Identity and auth: the agent's own, narrow identity">

For R7 and R2, the agent runs as its own agent identity, so audit logs name it.
It holds only the roles its tools need: calling the payments API and the Toolbox query, and searching the data
store. A Principal Access Boundary caps what it could ever reach. The payments
API is the company's own resource, and the agent acts as itself there, so its
calls use two-legged OAuth. Customers sign in to the website, not to Google
Cloud. The customer boundary for R2 is enforced by the query's parameter, from
the step on tools.

</Step>
<Step id="capstone-guardrails" title="Gateway and guardrails: control the traffic, screen the text, gate the refund">

For R7, the agent and its MCP server are registered in Agent Registry, and the
agent is bound to Agent Gateway, so all its outbound traffic passes through it:
the model, Agent Search, sessions, the MCP server and the payments API. Access
policies allow exactly those targets, and every call is recorded. A Model Armor template screens
prompts and responses for prompt injection, and its Sensitive Data Protection
filter covers the card numbers in R4. Start with inspect only to tune it, then
switch to inspect and block before launch, under an organisation floor setting.
Blocking stops content from going further but does not redact what was already
received, so R4 also calls for advanced Sensitive Data Protection, which can
de-identify card numbers as well as detect them.
For R3, the refund limit lives in code, as the next section explains.

</Step>
</Steps>

## The refund limit: where a rule is enforced

R3 is the decision that most often goes wrong. Writing "ask a manager before
refunds over $200" in the instruction is not enforcement: the model can skip
it, and an injected instruction can talk it out of it. The limit belongs in
code.

ADK's tool confirmation is the first tool to reach for. Wrap the tool with
`require_confirmation` set to a function that returns true when the amount is
over $200, and those calls pause until a person responds. But check the session
service: ADK's documentation lists `VertexAiSessionService`, which Agent
Runtime's managed sessions use, as not supported by this feature. So this
design puts the rule in `issue_refund` itself. At $200 or less it calls the
payments API. Above that, it files the refund in the support leads' approval
queue and tells the customer it is pending. Either way, code decides, not the
model.

<Callout type="tip">This kind of conflict between two good choices is what design reviews are for. Agent Runtime was chosen for R6 and tool confirmation for R3; reading the constraints of both together showed that they don't combine, and the design changed before anything was built.</Callout>

## Review a flawed design

A second team proposed this design for the same brief. Find five wrong choices
in it, then list every requirement that nothing in it covers. Write your list
down before you open the answers.

> An ADK agent on Cloud Run, autoscaling from 0 to 20 instances, with
> `InMemorySessionService`. It runs as the project's default compute service
> account, which has the Editor role. Tools: `execute_sql` against the orders
> database, and `issue_refund`. The instruction says: "Only show customers their
> own orders. Ask a manager before refunds over $200." Before launch, a reviewer
> reads 50 final answers and signs off.

<details>
<summary>Show the five wrong choices</summary>

1. **A broad, shared identity.** The default compute service account with Editor
   can change almost anything in the project, and audit logs cannot tell this
   agent from any other workload using the account. One successful injection
   reaches all of it. Fix: an agent identity holding only the roles its tools
   need, inside a Principal Access Boundary.
2. **Free-form SQL, with the customer boundary only in the instruction.**
   `execute_sql` lets the model write any query, so R2 depends on the model
   choosing to filter by the right customer. Fix: one parameterised query
   through MCP Toolbox, with the customer id taken from session state set at
   sign-in.
3. **The refund limit only in the instruction.** It is a request to the model,
   not a control. Fix: the limit in the refund tool's code.
4. **Sessions in instance memory.** With 0 to 20 instances, a later turn can
   reach another instance, and scale-to-zero recycles them all: a customer
   halfway through a refund starts over. Fix: a persistent session service, or
   Agent Runtime's managed sessions.
5. **A one-time review of final answers.** Reading answers cannot see a refund
   made without a lookup, and a one-time review tests none of the weekly
   changes in R5. Fix: an evalset with expected trajectories, run in CI on every
   change, plus online monitoring after launch.

</details>

<details>
<summary>Show the requirements nothing covers</summary>

- **R1:** no data store, so the policy questions have no source and the model
  answers from memory.
- **R4:** no screening, so card numbers are echoed and logged.
- **R7:** no gateway or registry, so security can neither see nor control what
  the agent reaches.

A requirement with no design element behind it is as much a defect as a wrong
choice, and easier to overlook, because there is nothing on the page to
question.

</details>

## Recap

- Number the requirements, and make every design choice cite one.
- Choose the least you must build and operate that still meets the brief:
  managed model, Agent Search, one agent, a managed runtime.
- Enforce rules in code, such as query parameters and tool logic, never only in
  the instruction.
- Design evaluation, identity and guardrails in from the start.
- Read the constraints of your choices together. Two good choices can conflict.
- In a review, look for wrong choices and for requirements with nothing behind
  them.
