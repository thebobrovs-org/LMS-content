## Not everything with an LLM is an agent

Teams call almost any feature that uses a large language model an "agent". That
label matters. Every LLM feature needs evaluation and protections suited to its
data and outputs, but an agent adds more: checks on the path it took, permissions
for the actions it can take, and guards against errors that compound over many
turns. And a task that a simple workflow handles well becomes
slower, costlier and harder to test when you make it an agent. Many of the
architecture choices in this path start with one question: **does this task need
an agent at all?**

## The parts of an agent

The tool-using <Term id="agent">agents</Term> this path studies have four core
parts, plus state. Google's Agent Development Kit (ADK) names the first three as
an agent's basic components, with tools optional: an ADK agent needs only a model
and instructions, but without tools it can only produce text, never read live data
or act. ADK's agent class is a building block, not a verdict: a tool-less ADK
agent that answers whatever the user asks behaves as a chatbot in this lesson's
terms.

- **A model** that reads the situation and reasons about what to do.
- **Instructions** that set the goal, the persona and the limits.
- **<Term id="tool">Tools</Term>** that let it read data or act: functions,
  APIs, databases, even other agents.
- **A loop.** The model picks the next tool call, the runtime (your code or the
  agent framework) runs it, the
  result comes back, and the model decides again, until it can answer or a stop
  condition ends the loop.

Around these four, **state** (the conversation so far, and longer-term memory) lets
each turn build on the last.

<Callout type="note">The model never runs a tool itself. It asks for a call, and your code, the agent runtime or the provider's tool service executes it. A later topic, the agent loop, follows one request through this cycle.</Callout>

## Chatbot, workflow or agent

The defining question is **who controls the path**: who decides what happens next.

<Figure

  alt="A left-to-right spectrum of system autonomy, from chatbot to workflow to agent. Chatbot: the user decides; answers each message and acts only when asked; simple and low risk, but the user directs each next step. Workflow: the designer decides; paths laid out in advance, with models filling steps or picking branches; predictable and testable but breaks when the path cannot be known ahead. Agent: the model decides; directs its own steps and tool calls in a loop; handles open-ended tasks but is less predictable and needs evals and guardrails."
  caption="The determinism spectrum: moving right, the system decides more for itself, which buys flexibility and costs predictability in what it does."
/>

- A **chatbot** answers each message. It acts only when the user asks, and the
  user decides every next step.
- A <Term id="workflow">workflow</Term> runs steps the designer laid out in
  advance. A step can call a model, for example to extract fields or draft a
  reply, and a model may even pick between branches the designer defined, but it
  never invents the path. That makes it predictable and easy to test. A single
  model call is simpler still, and often enough.
- An **agent** lets the model direct its own steps at run time. Where a
  workflow's router makes one choice among branches the designer wired, an agent
  chooses again and again in a loop, each choice informed by the last result. It
  can handle a
  task whose path you cannot know ahead of time, such as investigating a problem
  where each finding decides the next check.

<Callout type="note">ADK uses "workflow" more broadly: any application with more than one agent or executable node, including agents that route between themselves. This lesson uses the narrower sense above, where the designer controls the path.</Callout>

These sit on a <Term id="determinism spectrum">determinism spectrum</Term>, and
real systems mix them: a workflow with one agentic step, or an agent whose risky
actions pass through a fixed approval step.

## What autonomy costs

Each step to the right on the spectrum, above all from workflow to agent, hands
the system more control of what it does. That buys flexibility and costs
something:

- **Predictability.** The same input can take a different path on a different day.
- **Testing effort.** You must check the path the agent took, not just its final
  answer.
- **Latency and cost.** More model turns mean more time and more tokens.
- **Risk.** An agent that can act can act wrongly, and errors can compound over
  many turns, so it needs narrow permissions and guardrails. A limit written in
  the prompt is only guidance the model can ignore or be manipulated past, so
  enforce it in the tool or with an approval step.

So the rule is simple: **use the least autonomy that solves the task.** Start
with a single model call or a workflow, and give the model control of the next
step only where the path really cannot be known in advance. The rest of this
path teaches the tools for each choice: low-code workflows and agents, agents
built in code, and the evaluation and security layers that make autonomy safe to
ship.
