## Two protocols, two boundaries

The ADK lesson (topic 3.2) composed agents inside one app: a sub-agent takes over the
conversation, and an AgentTool is called like a function. Both run in your
process, from code you own. Real systems also cross two other boundaries.

- **Agent to tool.** The agent calls a function with typed arguments and gets a
  result: query a table, book a pickup. The **Model Context Protocol
  (<Term id="mcp">MCP</Term>)** standardises this. An MCP server publishes tools
  with names, descriptions and parameter schemas; an agent lists them
  (`tools/list`) and calls them.
- **Agent to agent.** The agent asks another agent, often run by another team or
  company, to do a piece of work. That agent has its own model, tools,
  instructions and state, and it may take minutes, ask a follow-up question or
  return files. The **Agent2Agent protocol (<Term id="a2a">A2A</Term>)**
  standardises this.

The A2A project puts it this way. MCP is vertical: it deepens a single agent.
A2A is horizontal: it connects agents across a boundary. A2A is an open project
under the Linux Foundation, contributed by Google, and its current specification is
version 1.0.

## What A2A exchanges

An A2A client sends a **message** (a role and one or more parts: text, a file
or structured data) to a remote agent. The remote agent's work is a **task**,
which moves through states: `submitted`, `working`, `input-required` (it needs
an answer from the client), `auth-required` (it needs further credentials), and
finally `completed`, `failed`, `canceled` or `rejected`. Its **artifacts** are
the files or structured data the task produces. Long work can stream updates
over server-sent events (a long-lived HTTP response the server keeps writing
updates to), or send push notifications (the server calls a URL you registered
when the task changes), so the client does not have to keep asking.

The remote agent stays **opaque**: the client sees its advertised skills, never
its prompts, tools or reasoning. That is the point. The finance team can change
its model or tools without breaking yours, and keeps its internals private.

## The agent card

A client finds out how to work with a remote agent from its
<Term id="agent card">agent card</Term>: a JSON document the A2A server
publishes, usually at `https://{domain}/.well-known/agent-card.json`. Here is a
shortened card for the finance team's fraud-review agent (A2A 1.0 field names):

```json
{
  "name": "Fraud review agent",
  "description": "Reviews a refund request for fraud risk and returns approve, reject or escalate, with reasons.",
  "version": "1.2.0",
  "supportedInterfaces": [
    {
      "url": "https://fraud-review.example.com/a2a",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0"
    }
  ],
  "capabilities": { "streaming": true, "pushNotifications": false },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "review-refund",
      "name": "Review a refund",
      "description": "Assesses one refund request against order and payment history.",
      "tags": ["fraud", "refunds"]
    }
  ],
  "securitySchemes": {
    "google": {
      "openIdConnectSecurityScheme": {
        "openIdConnectUrl": "https://accounts.google.com/.well-known/openid-configuration"
      }
    }
  },
  "securityRequirements": [{ "schemes": { "google": { "list": ["openid"] } } }]
}
```

- **Identity:** `name`, `description` and `version` say what the agent is.
- **Endpoint:** `supportedInterfaces` gives the URL, the protocol binding (the wire
  format and transport requests use: JSON-RPC, gRPC or HTTP+JSON) and the A2A
  protocol version that interface speaks.
- **Capabilities:** whether it streams or sends push notifications.
- **Skills:** what it can do, described for the calling agent's model, much as a
  tool's description is.
- **Security:** `securitySchemes` defines the authentication methods, here
  OpenID Connect (an identity layer on OAuth 2.0 that issues signed ID tokens),
  and `securityRequirements` says which of them the server requires. The card
  holds no secrets: the client obtains credentials separately, such as a token
  from the identity provider, and sends them with every request. The server
  authenticates each request against the requirements its card declares; the
  card only declares them, so the server's own code must enforce them.

Cards are also how agents are **discovered** at scale. Agent Registry, Google
Cloud's catalogue of agents and MCP servers, indexes
A2A agent cards alongside MCP servers, and agents deployed on Agent Runtime
(Google Cloud's managed service for running agents) are registered there
automatically. Gemini Enterprise, Google's workplace agent app, lets an
administrator add an A2A agent by entering its card. Check which A2A version a
product supports: Gemini Enterprise supports A2A 0.3's streaming mechanism, so
a 1.0 agent also advertises a 0.3 interface, using the compatibility packages.

## Local or remote: three designs for one scenario

The support agent needs three kinds of help:

| Need | Design | Why |
|---|---|---|
| A returns specialist your team owns, which should take over once a return starts | **Sub-agent** | Same code and release, and control should pass to it |
| A summariser your team owns, whose result comes back to the support agent | **AgentTool** | Same code, and the caller keeps control |
| The finance team's fraud-review agent | **<Term id="remote agent">Remote agent</Term> over A2A** | Another team owns, deploys, scales and secures it |

| | Sub-agent | AgentTool | Remote A2A agent |
|---|---|---|---|
| Runs in | Your process | Your process | Another service |
| Owned by | You | You | Often another team |
| Coupling | Shared code and release | Shared code and release | Only the card and the protocol |
| Identity | Your app's | Your app's | Authenticated per request, as the card requires |
| Latency | In process | In process | A network call, possibly a long task |

Go remote when another team owns, scales or secures the agent, not merely
because a capability sounds separate. Every remote hop adds latency, a
deployment and an authentication path to keep working.

## A2A in ADK

ADK can serve an agent over A2A and call a remote one. To serve the
fraud-review agent, the finance team wraps it in its `agent.py`:

```python
from google.adk.a2a.utils.agent_to_a2a import to_a2a

a2a_app = to_a2a(fraud_review_agent, port=8001)  # local test: uvicorn agent:a2a_app --port 8001
```

`to_a2a` builds an agent card from the agent's name, description and tools
unless you pass your own. By default the card advertises `http://localhost`, so
a deployed agent passes its real `host` and `protocol`, or its own card. On the calling side, a remote agent joins your agent
like a sub-agent, but every turn crosses the network:

```python
from google.adk.agents import LlmAgent
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

fraud_review = RemoteA2aAgent(
    name="fraud_review",
    description="Reviews refund requests for fraud risk. Use before approving a refund over 200 EUR.",
    agent_card="https://fraud-review.example.com/.well-known/agent-card.json",
)

support_agent = LlmAgent(
    name="support_agent",
    model="gemini-flash-latest",
    instruction="You help customers with orders and refunds.",
    sub_agents=[fraud_review],
)
```

The finance team can host its agent on Cloud Run (Google Cloud's serverless
container service) or on Agent Runtime, both of
which document A2A agents (in Preview at the time of writing).

<Callout type="note">A2A is young and moving fast: agent card field names differ between specification versions, and A2A hosting on Agent Runtime and Cloud Run, and A2A registration in Gemini Enterprise, are in Preview. Check the version each product supports before you rely on a field name.</Callout>
