## Data is what makes the agent useful

An agent can only answer from what it can reach, and it is only safe if it reaches
no more than the person asking could. In Gemini Enterprise both depend on three
pieces, and scenario questions turn on keeping them apart.

## Apps, data stores and connectors

- An **app** is what users work with: Google describes it as providing search
  results, actions and agents to end users. (In the API it is called an engine.)
- A <Term id="data store">data store</Term> holds the content an app searches. A
  store holds one type of data, and apps and stores are many-to-many: one app can
  search several stores, and a store can serve several apps.
- A <Term id="connector">connector</Term> brings content from a source into
  Gemini Enterprise, as one or more data stores (often one per kind of item, such
  as issues and comments). Google's docs also call third-party stores "data
  connectors"; don't let the name blur the two roles.

Connectors work in one of two ways, and some support both:

- **Federated:** each query is sent to the source system, which returns live
  results. Nothing is copied, but search quality can be lower.
- **Ingestion:** content is copied into Gemini Enterprise's index and kept in sync,
  by default with an incremental sync every three hours. Search quality is usually
  better, at the cost of storage and sync time.

## Choosing the store type

| Source | Data store type |
|---|---|
| Rows in a BigQuery table, or JSON records | **Structured**: imported from BigQuery or Cloud Storage, or sent through the API |
| Documents (PDF with embedded text, HTML, text; Word and PowerPoint in Preview) | **Unstructured**: imported from Cloud Storage or BigQuery, or synced from Google Drive |
| Jira, Confluence, SharePoint, Salesforce, Slack and similar apps | **Third-party connector**: Google treats this data as structured |
| A public website | Not a Gemini Enterprise store: website data stores can't be connected to its search and assistant apps |

The last row is a common trap. Website search, with domain verification for
generative answers, is a feature of **Agent Search**, Google's managed enterprise
search and retrieval service (formerly Vertex AI Search). Agent Search and Gemini
Enterprise use the same underlying API (Discovery Engine), but a Gemini Enterprise
app doesn't take a website data store. To use a site's content there, bring it in
another way, such as exported documents in Cloud Storage.

## Blended search

<Term id="blended search">Blended search</Term> connects several data stores to one
app, so a single query searches across sources and types of data. Users can search
everything at once or filter to one store. A few rules apply:

- Every store keeps its own type.
- Unstructured data imported through BigQuery can't take part.
- If one store uses a customer-managed encryption key (CMEK, a key you manage
  yourself), all the others must use the same configuration.
- Blended search is rate-limited in the Standard and Frontline editions; unlimited
  blended search needs the Plus edition.

## Permission-aware retrieval

The rule that matters most: **an agent must never widen what a user can read.**
Gemini Enterprise filters results per user, which needs two things:

- **Who is asking.** Gemini Enterprise uses your identity provider (IdP) to
  identify the person searching. If you connect that provider through a workforce
  identity pool (Google Cloud's way of letting users from an external identity
  provider sign in), you name the pool in Gemini Enterprise.
- **Who may read each document.** For connector stores, the connector brings the
  source's permissions along: the Jira connector, for example, maps Jira's
  permissions so only authorised users can search what it ingested, and an identity
  sync records which users belong to which groups. For data you import yourself
  from Cloud Storage or BigQuery, you add access lists (ACLs) to each document,
  naming the users and groups who may read it, and mark the store as
  access-controlled when you create it (this can't be added later).

Two ways this goes wrong in practice: importing your own documents without ACLs,
so nothing limits who sees them; and trusting a connector past its documented
limits, such as Jira attachments on private comments, which don't inherit the
comment's restrictions. Check the connector's documented limits before you index
sensitive sources.

<Callout type="warning">Permission filtering is only as good as the ACLs behind it. Before an agent goes live on a new source, test it as a user who should not see a sensitive document, and confirm the document never appears.</Callout>

## Images, video and audio

Multimodal content enters in two main ways:

- **In the conversation.** Users can upload files to the Gemini Enterprise
  assistant (its chat interface) and ask about them: documents (PDF, Office files,
  text, code), images (PNG and JPEG, up to 30 MB), video (MP4, up to 200 MB) and
  audio (MP3, up to 200 MB), with a combined limit per chat session of 800,000
  tokens (the units a model counts its input in). They can also chat with files
  stored in connected Drive, SharePoint and Box.
- **In the data store.** Unstructured stores are for documents (Google mentions
  images too). A layout parser can read text inside images in PDFs, such as
  infographics, but the documented import formats are documents, not video or
  audio files.

A Workflow Builder agent can also carry files as knowledge. These are loaded
straight into the model's context on every turn, up to a combined 800,000 tokens,
rather than searched like a data store.
