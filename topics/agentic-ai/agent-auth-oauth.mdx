## Whose authority does this call use?

The last lesson gave the agent its own identity and narrow roles on Google
Cloud. But many tools call APIs outside your project, or reach data that
belongs to a user: their calendar, their mailbox, their files. For every such
call, the architect decides **whose authority it uses**: the agent's own, or a
user's who agreed to it.

That decision is made with OAuth 2.0.

## OAuth authorises; OpenID Connect identifies

<Term id="oauth 2.0">OAuth 2.0</Term> is an authorisation framework. It lets an
application obtain limited access to an HTTP service, either on behalf of a
resource owner (a user who approves it) or on its own behalf. The application
gets an **access token**: a credential for specific protected resources, with
specific **scopes**, that it presents on each call. The user's password is not
part of it.

<Term id="openid connect">OpenID Connect</Term> (OIDC) is an identity layer on
top of OAuth 2.0. It adds an **ID token**, which carries claims about how the
user signed in. Use it when the application must know **who** the user is.

| | OAuth 2.0 | OpenID Connect |
|---|---|---|
| Answers | What may this client access? | Who is the user? |
| Main token | Access token, sent to the API | ID token, read by the client |
| Typical agent use | A tool calling an API | An app knowing which customer is signed in |

One Google Cloud exception: a private Cloud Run service or function behind IAM
expects an ID token whose audience is the service URL, not an access token. ADK
tools can be configured to send one.

## Two legs or three

**Two-legged OAuth (2LO)** and **three-legged OAuth (3LO)** are common
shorthand, used in Google's documentation, for two OAuth grants.

**Two-legged OAuth (2LO)** uses the **client credentials** grant. The agent
authenticates as itself, with no user involved, and gets a token for resources
under its own control. Use it when the agent acts as itself: writing to its own
bucket, calling an internal API on its own behalf. On Google Cloud the agent
usually does this as its **service account** rather than with a client secret:
it gets a token by signing a JWT (the JWT bearer grant) or from the metadata
server, and Application Default Credentials picks the method for you. Either
way no user is involved, so the shape is the same: the agent's own authority.

**Three-legged OAuth (3LO)** uses the **authorisation code** grant with user
consent. The third leg is the user. The user signs in at the authorisation
server and approves specific scopes; the application receives a code and
exchanges it for a token that acts for that user. Because the user
authenticates only with the authorisation server, their credentials are never
shared with the application, or with the agent. Use it when the agent touches a
user's data.

The rule: **3LO when the agent acts on a user's data with their consent; 2LO
when it acts as itself.** Using one powerful credential to read every user's
data is the excessive agency from the threat model lesson. Three-legged OAuth
keeps the agent to what each user agreed to.

### An example: data agents that query as the user

Google's Conversational Analytics API, which answers questions over BigQuery
and Looker data, shows the rule in practice. When an agent platform reaches it
through a remote MCP server, the platform signs the user in with three-legged OAuth and passes the
user's delegated access token with each request. BigQuery queries then run as
that user, not as a shared service account, so the user's IAM permissions and
row-level and column-level security policies apply without extra code.

Looker works differently. A query runs with the credentials configured for it:
with Looker API keys (a client ID and secret), every user gets that API user's
access. To apply each user's own LookML row and column permissions, send that
user's access token instead.

## Six auth models on Google Cloud

Google's Agent Identity documentation sorts every call an agent makes by two
questions: **whose authority** it uses, and **what the target accepts**.

| Authority | Method | Target | Use it when |
|---|---|---|---|
| User-delegated | OAuth 2.0, 3-legged | External tools | The agent acts for one user, such as on their Jira or GitHub. An auth provider handles consent and tokens. |
| Agent's own | Agent Identity | Google Cloud APIs | The agent calls Google Cloud with its own principal and grants. |
| Agent's own | OIDC ID tokens | External tools | The agent calls an external backend or another cloud that trusts Google's OIDC identity federation. |
| Agent's own | OAuth 2.0, 2-legged | External tools | Machine to machine, where the service supports OAuth. Google recommends this one for external services. |
| Agent's own | API key | External tools | The service only takes a key. The auth provider stores and manages it. |
| Agent's own | HTTP basic auth | External tools | Only if nothing else is offered: it sends plaintext passwords, and Google marks it not recommended. |

The first two rows are what the previous lesson and this one have covered so
far: 3-legged OAuth for a user's data, and the agent's own Agent Identity for
Google Cloud. The OIDC row is the same identity carried outside Google as a
signed ID token, which the receiver checks against public keys. The last three
rows hold a third party's secret: the **auth manager**, below, keeps it out of
your code.

Behind the table sit three identities. The **user identity** signs in to your
app with OAuth 2.0 or OIDC. The **agent identity** is the agent's SPIFFE-based
principal, acting on its own authority. The **delegated identity** is the agent
acting for the user with scoped 3-legged credentials that the auth manager
brokers. Audit logs record both the agent and the delegating user.

## Tool authentication in ADK

ADK describes a tool's authentication with two objects:

- **AuthScheme**: how the API expects credentials, such as an OAuth 2.0 bearer
  token, an API key or OpenID Connect. ADK supports the same scheme types as
  OpenAPI 3.0.
- **AuthCredential**: the initial information to start the flow, with a type
  such as `OAUTH2`, `OPEN_ID_CONNECT`, `SERVICE_ACCOUNT` or `API_KEY`. For
  OAuth that is your application's client ID, client secret and scopes.

An <Term id="authconfig">AuthConfig</Term> pairs the two for one tool or a
whole toolset. ADK then tries to exchange the credential for a token before the
tool calls the API. For two-legged OAuth or a service account, that exchange
needs no person. For three-legged OAuth, it needs the user, so the agent
pauses.

### The consent pause and resume

<Steps>
<Step id="auth-step-declare" title="The tool declares how it authenticates">
The tool or toolset carries an AuthScheme and an AuthCredential (an
AuthConfig), for example OAuth 2.0 with your app's client ID, secret and the
scopes it needs.
</Step>
<Step id="auth-step-request" title="The first call finds no token and requests one">
The session holds no valid credential for this user yet, so ADK pauses the run
and emits an `adk_request_credential` event to your client app, carrying the
AuthConfig and its authorisation URL.
</Step>
<Step id="auth-step-consent" title="The client app sends the user to consent">
Your app appends its registered redirect URI to the authorisation URL and opens
it. The user signs in at the provider and approves the scopes. The provider
redirects back with an authorisation code.
</Step>
<Step id="auth-step-return" title="The client app returns the auth response">
Your app captures the callback URL and sends it back to ADK as the function
response to `adk_request_credential`.
</Step>
<Step id="auth-step-resume" title="ADK exchanges the code and retries the tool">
ADK exchanges the code for an access token (and possibly a refresh token),
makes it available to the tool, and automatically retries the original call.
The agent answers with the real result.
</Step>
</Steps>

Two points matter for the architecture. The **agent never sees the user's
password**: it receives a token limited to the approved scopes. And the
**client app owns the consent step**: a chat window alone cannot complete it,
so the app must handle the event and a redirect URI.

### Where tokens and secrets live

Tokens and client secrets are credentials, so treat them like the agent's
other secrets. ADK's documentation recommends an **authentication manager**
service in production: one that stores keys and secrets and acquires, manages
and stores OAuth tokens for you. If you manage tokens yourself, store them
encrypted against an authenticated user, and keep secrets in a secrets manager,
not in code, prompts or a `.env` file outside local development.

## The auth manager: one broker for third-party credentials

Agent Identity's **auth manager** is Google's authentication manager for
agents, and it integrates with ADK (the ADK integration was in Preview at the
time of writing). You configure an **auth provider** for each third-party app:
its type (3-legged OAuth, 2-legged OAuth or API key) and its credentials, such
as an OAuth client ID and secret, a token URL or a key. The auth manager then:

- keeps API keys, OAuth client secrets and users' tokens in a **Google-managed
  vault**;
- runs the multi-step OAuth work itself: consent, the authorization code
  exchange and token refreshes, with no backend code of yours;
- lets you see which users granted access, and revoke it.

Who may use a provider is ordinary IAM: grant the Agent Identity User role
(`roles/agentidentity.user`) on the auth provider to the agent's principal (and,
for 3-legged OAuth, to the users). Auth providers live in a region, not in
`global`, so keep the provider, the MCP server and the Agent Registry client in
one region. When a tool comes from an MCP server in Agent Registry, the
server's outbound binding already records which auth provider to use, so you
don't build an auth scheme for it.

**2-legged OAuth and API key providers** use the agent's identity and need no
consent: ADK retrieves the token or key from the provider and injects it into
the tool's request headers. **3-legged providers** need the user once. Follow
Ana's first request in **Ana's GitHub token through the auth manager**:
predict where her tokens end up, then step through the pause, her consent on
GitHub's own page, and the callback. Step 9 shows her next request.

<Simulation id="auth-manager-flow" />

**Explain it:** in Ana's flow, the app and the agent each take part, yet
neither ever holds her GitHub tokens or the OAuth client secret. What does each
of them do, and what does the auth manager do in their place?

The pieces you build for a 3-legged provider:

1. **Register the callback.** Creating the auth provider returns its
   `oauthcallback` URL on `agentidentitycredentials.googleapis.com`; register
   it as the redirect URI of your OAuth client at the third party.
2. **Handle the pause.** When the agent returns `adk_request_credential`, the
   app sends the user to the `authorization_uri` and keeps the `consent_nonce`.
3. **Serve a continue URI.** After consent the user lands on your app's
   `continue_uri`, which calls `FinalizeCredentials` with the nonce to complete
   the flow.
4. **Resume the agent** with a `function_response` to `adk_request_credential`.
   ADK fetches the token from the provider and the tool call runs.

<Callout type="warning">A common trap: "the user can just give the agent their password". Then the agent holds a credential that does everything the user can do, until the password changes, and the model has seen it. Three-legged OAuth gives it a token for only the scopes the user approved, which the user can usually revoke at the provider.</Callout>

## Recap

- OAuth 2.0 authorises access with tokens; OpenID Connect adds an ID token that
  says who the user is.
- Two-legged (client credentials, or a service account on Google Cloud): the
  agent acts as itself. Three-legged (authorisation code with consent): the
  agent acts for a user, on that user's data.
- In ADK, an AuthConfig pairs an AuthScheme and an AuthCredential. A
  three-legged tool pauses with `adk_request_credential`, the client app gets
  consent, and ADK exchanges the code and retries the call. The agent never
  sees a password.
- Keep tokens and secrets in an authentication manager or a secrets manager.
- Google's six auth models follow from two questions: whose authority, and
  what the target accepts. 3-legged for a user's data; Agent Identity for
  Google Cloud; OIDC ID tokens, 2-legged OAuth or an API key for external
  services on the agent's own authority; basic auth only as a last resort.
- Agent Identity's auth manager holds third-party secrets and users' tokens in
  a Google-managed vault, runs consent and code exchange through an auth
  provider's callback, refreshes tokens, and lets ADK inject them into tool
  calls.
