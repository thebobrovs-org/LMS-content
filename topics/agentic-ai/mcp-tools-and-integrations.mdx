## Why agents need integrations

An agent is useful only when it acts on real systems: reading orders, querying
analytics, booking a pickup. In topic 3.2 each of those was a Python function
inside the agent. That works for one agent, but every team ends up rewriting the
same database and API wrappers, each with its own credentials and its own bugs.

The <Term id="mcp">Model Context Protocol (MCP)</Term> is an open standard for
offering tools to agents. An **MCP server** publishes a set of tools, each with
a name, a description and a parameter schema; an **MCP client**, such as an ADK
agent, lists those tools, offers them to the model and calls them when the model
proposes one. The loop from topic 3.1 does not change: the model proposes, the
runtime executes, but the execution now happens in the MCP server. Write the
server once, and any MCP-capable agent can use it.

A server can run as a local process the client starts and talks to over
standard input and output (the **stdio** transport), or as a remote service the
client reaches over HTTP (the **streamable HTTP** transport). Agents in
production use remote servers.

## Three routes, three owners

Take the support agent from topic 3.2 and give it three new capabilities. Access
on Google Cloud is controlled by IAM (Identity and Access Management), which
grants identities roles that decide who may call what.


| Capability | Route | Who hosts and updates it | Who secures it |
|---|---|---|---|
| Query sales analytics in BigQuery | A **Google Cloud MCP server** (BigQuery's) | Google | IAM roles you grant on your project |
| Look up one customer's order in the orders database | **MCP Toolbox for Databases**, with named queries | You run the open-source server; you write the queries | You: database account, query design, caller authentication |
| Book a pickup through the internal carrier API | A **custom MCP server** | You build, host and patch it | You, end to end |

**<Term id="google cloud mcp servers">Google Cloud MCP servers</Term>** are remote MCP servers that run on Google's
infrastructure and offer an HTTP endpoint for a Google Cloud service, for
example BigQuery, Cloud SQL, Spanner, GKE or Cloud Storage. You enable the
product's API, and access goes through IAM: the caller needs the MCP Tool User
role plus the product's own roles. To keep an agent to read-only tools, an IAM
deny policy can block every tool that is not marked read-only. When a server
exists for the service, use it: Google runs and updates it, and you only manage
access.

**<Term id="mcp toolbox for databases">MCP Toolbox for Databases</Term>** is an
open-source MCP server that connects agents to databases (AlloyDB, BigQuery,
Cloud SQL, Spanner, PostgreSQL, MySQL and many more). You describe each tool in
a configuration file: the source, a fixed SQL statement and its parameters.
Choose it when the agent needs specific queries against your own tables.

**A custom MCP server** wraps an internal API that nothing else covers. Build it
with an MCP SDK and host it where agents can reach it over HTTP. Cloud Run
(Google Cloud's serverless container service) supports MCP servers that use
streamable HTTP, not stdio, and requires an IAM identity on every request by
default. A common layout runs the agent on Agent
Runtime (Google Cloud's managed service for running agents) and the MCP server
as a separate Cloud Run service.

<Flashcard id="route-order-inline" objective="choose-integration" front="A Google Cloud service already has a remote MCP server. Why use it rather than write your own?" back="Google hosts and updates it; you only manage access, by granting IAM roles. Writing your own rebuilds the same tools and leaves your team to host, secure and patch them." />

## Database tools: named queries, never free-form SQL

The fastest way to connect an agent to a database is one tool that runs any SQL
the model writes. It is also the most dangerous. The model can read every table
the database account can, run an `UPDATE` that text it retrieved talked it into,
(a prompt injection), or return another customer's rows. MCP Toolbox's own execute-SQL tools carry the
warning that they are for developer workflows with a human in the loop, not
production agents.

Give the agent **named, parameterised queries** instead: each tool has a fixed
statement, and the model only supplies typed values, which are bound as query
parameters, never spliced into the SQL. Here is the order lookup as an MCP
Toolbox configuration (one YAML document per source, auth service and tool):

```yaml
kind: source
name: orders-db
type: cloud-sql-postgres
project: my-project
region: europe-west1
instance: orders
database: orders
user: ${DB_USER}
password: ${DB_PASSWORD}
---
kind: authService
name: customer-auth
type: google
clientId: ${OAUTH_CLIENT_ID}
---
kind: tool
name: get-my-order
type: postgres-sql
source: orders-db
description: Returns the status and tracking id of one of the signed-in customer's orders. Use when the customer gives an order id.
parameters:
  - name: order_id
    type: string
    description: The order id, for example A1234.
  - name: customer_id
    type: string
    description: The signed-in customer's id.
    authServices:
      - name: customer-auth
        field: sub
statement: SELECT status, tracking_id FROM orders WHERE order_id = $1 AND customer_id = $2;
```

Three choices make this safe:

- **A fixed statement.** The agent can run this one `SELECT` and nothing else.
  Add one named tool per action the agent needs.
- **An authenticated parameter.** `customer_id` is filled from the caller's
  verified Google OIDC token (a signed identity token whose `sub` claim is the
  user's unique id), not by the model. A user who types
  someone else's id into the chat still gets only their own orders.
- **Secrets from the environment.** The database user and password come from
  environment variables (in production, a secret manager), never from the file.

Also give the database account only the privileges the tools need, such as
read access to the `orders` table.

<Flashcard id="authenticated-parameter" objective="database-tools" front="What is an authenticated parameter in MCP Toolbox?" back="A tool parameter whose value Toolbox fills from a claim in the caller's verified token (for example the user's id), instead of letting the model supply it. The model cannot change whose data the query reads." />

An ADK agent loads these tools from a running Toolbox server, and loads a remote
MCP server's tools through `McpToolset`:

```python
from google.adk.agents import LlmAgent
from google.adk.tools.mcp_tool import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StreamableHTTPConnectionParams
from google.adk.tools.toolbox_toolset import ToolboxToolset
import google.auth.transport.requests
from google.oauth2 import id_token

orders_tools = ToolboxToolset(
    server_url="https://toolbox-orders.example.run.app",
    # get_user_id_token returns the signed-in user's Google ID token,
    # which Toolbox verifies to fill the authenticated customer_id parameter
    auth_token_getters={"customer-auth": get_user_id_token},
)

CARRIER_URL = "https://carrier-mcp.example.run.app"  # your custom server on Cloud Run

def carrier_auth_headers(ctx):
    # The agent's own service identity proves itself to Cloud Run: a fresh
    # ID token for the service's URL (its audience), on every new MCP session.
    token = id_token.fetch_id_token(google.auth.transport.requests.Request(), CARRIER_URL)
    return {"Authorization": f"Bearer {token}"}

carrier_tools = McpToolset(
    connection_params=StreamableHTTPConnectionParams(url=f"{CARRIER_URL}/mcp"),
    header_provider=carrier_auth_headers,
    tool_filter=["book_pickup", "get_pickup_status"],  # offer the model only these
)

support_agent = LlmAgent(
    name="support_agent",
    model="gemini-flash-latest",
    instruction="You help customers with their orders and returns.",
    tools=[orders_tools, carrier_tools],
)
```

`tool_filter` limits which of a server's tools the model is offered, so it sees
only the declarations it needs and cannot call the rest. It is not access
control: because the Cloud Run service requires IAM, the agent's own service
identity must be allowed to invoke it (the invoker role) and must also send an
identity token with each request, which is what `carrier_auth_headers` does. The
role alone attaches no token. This is a different boundary from
`get_user_id_token` above, which carries the end user's identity to Toolbox. The
security lessons later in this path cover agent identities.

## Register what agents may use

Once several teams build MCP servers, nobody can see which agents use what.
<Term id="agent registry">Agent Registry</Term> is the catalogue: it lists the
agents, MCP servers and their tools, and endpoints in your project or organisation.

- **Google Cloud remote MCP servers are registered automatically.**
- **Custom servers** register automatically in some cases: a Cloud Run service
  deployed with `--functional-type=mcp-server`, or a GKE workload with the
  matching label. Otherwise you register one yourself, with
  `gcloud agent-registry services create` and a tool spec file that describes
  its tools. The carrier server, deployed to Cloud Run with that flag, appears
  in the registry with its two tools and no extra step.
- **Governance:** access policies bind agent identities to the registered
  servers they may use, and Agent Gateway enforces them at runtime on agent
  traffic routed through it.
- **Discovery:** an ADK agent can look a registered server up and load its
  tools from the registry, instead of hard-coding a URL.
- **Search:** the registry searches registered agents, MCP servers and skills.
  MCP servers are found by keyword over the server's name and description and
  its tools' names and descriptions. Standalone skills can also be searched
  semantically (`--search-type=semantic`), a mode Google describes as
  optimised for orchestrator agents finding capabilities by intent.

Search matters because loading every tool does not scale. Google's
architecture guidance calls the problem <Term id="tool bloat">tool bloat</Term>:
too many tool definitions in the model's context, which overwhelm it and spend
tokens on every call. Its fix is progressive disclosure, unlocking tools only
when they are needed. One form is the **search tool pattern**: the agent gets a
single search tool and loads only the relevant tool schema when a task calls
for it, instead of declaring every tool up front. (Topic 3.8 measures what
declarations cost per call.)

<Flashcard id="tool-bloat" objective="register-tools" front="What is tool bloat, and what does the search tool pattern do about it?" back="Tool bloat is giving a model too many tool definitions, which overwhelms it and spends tokens on every call. The search tool pattern gives the agent one search tool that loads only the relevant tool schema when a task needs it, instead of declaring every tool up front." />

Registration does not host, scale or secure the server for you. It makes the
server findable and puts its use under policy, which is what lets a security
team answer "which agents can book pickups?"

<Callout type="note">MCP and its Google Cloud integrations move quickly: individual MCP servers, Agent Registry features and the MCP Toolbox configuration format have changed during 2026. Check each product's current page and launch stage before you rely on a detail.</Callout>
