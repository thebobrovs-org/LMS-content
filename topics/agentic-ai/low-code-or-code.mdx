## Real systems mix both

Production agent systems often mix low-code and code. A common shape is a low-code
experience that people use every day, in front of code-built agents and tools that
do the hard parts. Scenario questions test the judgement behind that split: when to
stay low-code, when to move to code, and how to join the two.

Low-code here means Gemini Enterprise's **Workflow Builder** (chat agents and
workflows built visually) and **CX Agent Studio** (customer-facing conversational
agents, with **flows**: fixed conversation paths, reused from Dialogflow CX, for
deterministic logic). Code means
the **Agent Development Kit (ADK)**, deployed to Agent Runtime, Cloud Run or GKE.

## Start low-code; move to code for control

Start low-code when the platform covers the need. Its steps, connectors and tools
do the job, the people who own the process can maintain it, and you get Gemini
Enterprise's sharing and governance without building them. Move to code when you
need control the platform cannot give.

The limits are concrete. Workflow Builder, for example, runs a chat agent's
sub-agents one at a time and only one level deep. A design that needs specialists
working in parallel, or a planner that delegates to agents that delegate again, has
outgrown it. Evaluation is the other common trigger. Workflow Builder is tested by
running simulations by hand, with no documented API for automated tests. CX Agent
Studio is further along: its test cases can be run through an API (in beta), but
they test the CX agent, not code you own. If logic you own must pass trajectory
tests (checks of the tool calls the agent made) in a pipeline on every change, that
logic needs to live in code beside its **evaluation sets**: files of test cases with
the expected answers and tool calls.

<Callout type="tip">The migration signals: logic the steps can't express, orchestration beyond the platform's limits, evaluation that must run in CI, control of deployment or networking, and an integration no connector or tool covers. A wish for better instructions is not one of them.</Callout>

## Three scenarios

- **IT helpdesk: stay low-code.** Employees ask how to reset a password or request
  a laptop, and the agent answers from the IT knowledge base and files a ServiceNow
  ticket through a connector (write actions pause for a person's review). The platform covers every part, and the IT team can
  maintain it. Code would add a build and deploy pipeline for nothing.
- **Insurance claims triage: code.** Three specialist agents check policy, damage
  photos and fraud signals at the same time, then a fourth decides. Every release
  must pass evaluation sets in CI. Parallel specialists and CI-gated evaluation are
  both beyond the low-code limits, so this is an ADK multi-agent system.
- **Sales quotes: hybrid.** Sales staff live in Gemini Enterprise, but pricing is a
  complex, tested calculation the finance engineers own. Keep the quote workflow in
  Workflow Builder, put pricing behind an MCP server, and call a registered ADK agent
  from an existing-agent step for the drafting that needs many tools. The figure below shows this design.

## Hybrid designs

A <Term id="hybrid agent">hybrid agent</Term> keeps the experience low-code and puts
the hard logic in code. Google documents several joins; the main ones:

- **A low-code agent calls code-built tools.** Workflow Builder has MCP steps, and a
  Gemini agent step can be given MCP tools to choose from. CX Agent Studio can call
  OpenAPI tools, and MCP servers that use streamable HTTP (MCP's HTTP transport;
  the older SSE transport isn't supported); for a server on Cloud Run, Google
  recommends authenticating with the CX service agent's ID token, granted the Cloud
  Run Invoker role. Put your logic behind an MCP server or an API, on Cloud Run for
  example, and the low-code agent calls it.
- **A low-code agent calls a code-built agent.** Workflow Builder's existing-agent
  step runs an ADK or A2A agent that has been published (registered) in Gemini
  Enterprise and shared with you, as one step of the workflow. CX Agent Studio can delegate a task
  to a remote ADK or A2A agent through an A2A tool.
- **A code-built agent appears in Gemini Enterprise.** Deploy an ADK agent to Agent
  Runtime and register it as a custom agent, or register an A2A agent by its agent
  card (the description an A2A agent publishes of itself). A2A registration is in
  preview, not yet generally available. Users then find the agent beside the
  low-code ones.

## Decide early where evaluation and identity live

Migrations rarely break the prompt. They break what was wrapped around it:

- **Evaluation.** Test cases written for a low-code agent don't run against an ADK
  agent. Rebuild them as evaluation sets, and keep the old and new agents scoring
  the same cases until the switch.
- **Identity.** A low-code agent acts inside the platform's sign-in and sharing. A
  code-built agent needs its own: whose permissions it uses, and an OAuth setup if
  it must act for the user.
- **Governance.** Settings can quietly stop applying. Google documents that Model
  Armor settings in the Gemini Enterprise console don't automatically protect
  registered ADK or A2A agents (they configure screening in their own code), and
  that traffic to a registered A2A agent bypasses Agent Gateway.

So when a design starts low-code but may grow, decide at the start where each of
these will live for every part of the system.
