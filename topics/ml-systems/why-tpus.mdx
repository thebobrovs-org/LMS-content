## The one-line summary

A TPU is a chip Google built to do one thing fast: the **matrix math** at the
heart of neural networks. You never touch the chip directly — you SSH into a
**host VM** that's wired to it, run your JAX or PyTorch code there, and it
dispatches the heavy work to the TPU.

## Why build special hardware at all?

Modern AI — both training and inference — is dominated by **matrix multiply at
enormous scale**. A general-purpose CPU spends most of its time shuttling operands
in and out of memory rather than computing (the *memory wall*). GPUs help, but
Google went further and built an <Term id="asic">ASIC</Term> tuned for exactly
this workload. The payoff is more matmul **throughput per watt and per dollar** —
which, at the scale of a flagship model, is the whole game.

You'll see *how* it wins in the next topic (the systolic array). Here, the goal is
the mental model: what a TPU is, and how you reach it.

## What a TPU is

A TPU is an <Term id="asic">ASIC</Term> — an application-specific integrated
circuit — **purpose-built for ML**, so it cannot run general-purpose code. Its
compute core is the <Term id="tensorcore">TensorCore</Term>:

- the <Term id="mxu">MXU</Term> (a systolic array — 128×128, so 16,384
  multiply-accumulates per cycle; bf16 in, fp32 out) where matmuls run,
- a <Term id="vpu">vector unit</Term> for activations, softmax, and elementwise
  math, and
- a scalar unit for control flow and addressing.

Memory is <Term id="hbm">HBM</Term>, and chips talk to their neighbours over
<Term id="ici">ICI</Term>. Use the interactive cutaway below to click each part
and read what it does — you'll come back to it in the exercises:

## How you actually use one: the TPU VM

You don't rent a bare chip — you get a **Linux host VM physically attached** to the
chips (on the 8th gen, an Arm-based **Axion** CPU, to keep data prep from
bottlenecking the accelerator). You <Term id="tpu vm">SSH in</Term> with root access, install JAX or
PyTorch-XLA, and run your program. It launches onto the TPU over PCIe and the
compute stays on-chip — **there is no per-operation network hop** to the
accelerator, because the host *is* the accelerator's host. (That's why later
orchestration is about scheduling these host+chip units, not about a remote API.)

## From one chip to tens of thousands

A TPU's power comes from ganging chips together. The ladder:

- **Chip** — one or more TensorCores plus HBM.
- **Host** — the VM you SSH into; it drives the chips attached to it.
- **Slice** — a block of chips wired by <Term id="ici">ICI</Term>.
- **Pod** — a contiguous set of chips on one ICI network (a torus — 3D on training chips such as v4/v5p, 2D on v5e/v6e — or a Boardfly topology for inference).
- **<Term id="multislice">Multislice</Term>** — multiple slices joined over the
  slower Data-Center Network (DCN) for jobs bigger than one Pod.

## Which TPU, and when

The **8th generation** makes this topic's point loudest: it **splits the chip by
workload** into two parts you choose between.

- **TPU 8t — training.** Keeps <Term id="sparsecore">SparseCores</Term> (for
  embeddings) plus an **LLM decoder engine** (silicon that accelerates token-by-token
  generation), on a 3D-torus network, with **native
  FP4** (4-bit float) that doubles MXU throughput; built for pre-training at
  superpod scale.
- **TPU 8i — inference.** Swaps the SparseCores for a
  <Term id="cae">Collectives Acceleration Engine (CAE)</Term> (≈5× lower on-chip
  collective latency), carries **3× the on-chip SRAM** (384 MB) to hold the
  <Term id="kv cache">KV cache</Term> — the per-token attention buffer that grows with
  sequence length — and uses the **Boardfly**
  network (≈7 hops across 1,024 chips vs 16 on a torus).

The same training-vs-inference logic runs back through the lineage: **v5e / v6e
(Trillium)** for cost-efficient **inference**, **v5p / v7 (Ironwood)** for
**training** (the MXU grew to 256×256 with Trillium, v6e). <Term id="sparsecore">SparseCore</Term>
accelerates the giant embedding lookups — table reads that map each token ID to its dense
vector, a gather pattern — in recommendation/ranking and MoE routing.
The takeaway isn't the part numbers — it's that *the box is tailored to the
workload*, which is why you reason about training vs serving from the silicon up.
