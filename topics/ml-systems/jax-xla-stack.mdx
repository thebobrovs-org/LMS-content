## The compile path

You write NumPy-like Python. The TPU runs machine code. Here's the bridge:

1. **Trace — on the host CPU.** When you first call a `jax.jit`-decorated function, JAX runs
   it once on the **host VM** — burning host **CPU and RAM**, with the TPU sitting idle — using
   *abstract* values to <Term id="tracing">freeze your dynamic Python into a static graph</Term>.
   This step exists because of a hardware mismatch: ordinary Python is dynamic and allocates
   memory on the fly, but a TPU is rigid — it needs strict, **pre-allocated
   <Term id="hbm">HBM</Term> layouts** *before* it will accept any work. Tracing freezes every
   tensor shape so XLA can compute exactly how many bytes of HBM to reserve. (Change an input
   shape and it re-traces and recompiles — the classic "why did my step suddenly get slow?")
2. **Lower to StableHLO.** *Lowering* is compiler-speak for translating a program down one
   rung toward the hardware (think source → IR → machine code). The trace first becomes a
   **jaxpr** — JAX's own internal op-list IR — which is then lowered to **StableHLO**, a
   portable, hardware-neutral IR. (That's the `Python → jaxpr → StableHLO` pipeline you'll
   step through in the simulation below.)
3. **Compile with <Term id="xla">XLA</Term> — also on the host.** XLA optimizes the StableHLO —
   most importantly it **<Term id="fusion">fuses</Term>** ops — and emits an executable for your
   target (TPU, GPU, or CPU — the *same* program). This compile *also* runs on the host's CPU and
   RAM; the **TPU chip stays completely idle** until XLA finishes and ships the binary over
   **PCIe**. (That's exactly why a **compilation cache** is worth so much on multi-host jobs —
   you don't want every host paying the same compile.)

You never hand-write a kernel. You shape the Python; XLA writes the silicon's code.

## Fusion: the optimization that matters most

A transformer layer is a matmul followed by a chain of cheap elementwise ops — bias, an
<Term id="activation function">activation</Term> like GELU, scale. Run them naively and
**every op re-reads its input from
<Term id="hbm">HBM</Term> and writes its output back** — a round-trip per op. Fusion
merges the chain into one kernel: the matmul reads its inputs once, the elementwise
work rides along in its *epilogue* (the tail end of the matmul kernel) on-chip, and only
the final result is written back.

<Callout type="tip">
**Infra engineers: skip the calculus.** You don't need to know *what* a GELU computes — only
its **systems profile**. Bias, GELU and scale are **element-wise** ops: one cheap arithmetic
operation per element, but each one reads the *entire* tensor from HBM and writes the entire
tensor back. That's almost no compute per byte moved — so on their own they're pure
**memory-bandwidth** traffic, and they stall the chip waiting on HBM. Unfused, this trivial
math becomes the bottleneck; fused, the bytes never leave the chip and the stall disappears.
</Callout>

Same FLOPs, far fewer bytes — exactly the
<Term id="arithmetic intensity">arithmetic intensity</Term> lever from the systolic-array
lesson. (The **ridge** is the roofline crossover point: below it you're *memory-bound* —
starved on HBM bandwidth; above it *compute-bound* — saturating the MXU.) Walk the compiler
pipeline, then run the race: the fused kernel makes fewer HBM trips, so it spends less time
stalled on memory — that shorter wall-clock per step **is** throughput you can measure.

## JIT vs AOT — and catching OOM before you spend a slice

Same compiler, two timings:

- **JIT** (`jax.jit`) compiles on the **first call** and caches the result. Convenient,
  but you only find out what it compiled to (and whether it fits in HBM) when that
  first call runs. Both modes compile on the host.
- **AOT** (`jax.jit(f).lower(args).compile()`) compiles **ahead of time**, *without
  running*. The payoff: the compiled object carries a **memory analysis** you can read —
  so you can discover that a batch size or sharding choice will **OOM a v5p slice at
  compile time**, before a single step burns real (and scarce) capacity.

On multi-host jobs, a **compilation cache** lets every host reuse one compile instead of
all of them paying the cost — a real startup-time win you'll meet again in the next
lessons.

## Where this sits in the stack

The compiler is the floor; everything above it is libraries. The vertical layering is
**your model code → JAX → StableHLO → XLA → TPU**. Flax and Optax aren't *rungs* in that
stack — they're **sibling libraries on top of JAX** (one builds the model, the other the
optimizer):

- **JAX** — the numerics and transforms (`jit`, `grad`, `vmap`) everything else builds on.
- **Flax NNX** — the model/module system (which Flax API the model is built in is the
  modeling team's call, not the operator's). **NNX is the recommended API** for new code;
  **Linen** is the older one that still powers frameworks like MaxText, so you'll read
  both. (Either way it's **XLA/JAX-first** — *not* "TPUs are for TensorFlow.")
- **Optax** — composable optimizers.
- **Orbax** and **Grain** — checkpointing and data loading (the next lesson's stars).

## Why this matters

Every later skill — SPMD sharding, fixing a starved input pipeline, debugging a
megascale run — assumes you can look at what the compiler produced and reason about it.
The engineer who treats XLA as magic guesses; the one who reads the HLO and the memory
analysis *knows*. That's the difference this level is built to create.
