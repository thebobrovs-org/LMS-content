## The one-line summary

Every later lesson — precision, shapes, sharding — leans on one word: **tensor**. It sounds
exotic. It isn't. To the hardware, a **<Term id="tensor">tensor</Term> is just a multidimensional
array of numbers** — a flat row of values in memory, plus a **shape** that says how to read them.
A single number, a list, a grid, a cube of numbers: all tensors, differing only in how many
**dimensions** they have. Get that, and "the model is just tensors flowing through chips" stops
being a slogan and becomes something you can reason about.

<Callout type="tip">
**Infra bridge.** You already think this way. A config value is one number. A time series is a
list. A routing table is a grid. Stack routing tables across VRFs and you've got a cube. Those are
ranks 0, 1, 2, 3 — the *only* thing that changes is how many indices you need to reach one value.
</Callout>

<Callout type="tip">
**Run it yourself.** A short [Colab notebook](https://colab.research.google.com/github/thebobrovs/LMS-content/blob/main/notebooks/what-is-a-tensor.ipynb)
reads a tensor's rank and shape straight off `numpy`, then computes the footprint and charts the
rank → memory blow-up (watch rank 3 punch through a chip's HBM). Pure `numpy`, runs on **CPU**, no GPU.
</Callout>

## From an arrow to an array — the shadow trick

So where do the numbers come from? Start with something physical: an **arrow** in space (a
direction with a length). You can't store an arrow — but you *can* measure its **shadow** on each
axis. Those shadow lengths are the arrow's **components**, and that list of components —
`[x, y, z]` — *is* the array the computer keeps.

<Simulation id="vector-basis-explorer" height={560} />

The shadow on an axis is called a **<Term id="projection">projection</Term>**; the little length-1
rulers (x̂, ŷ, ẑ — the caret ˆ just means "length exactly 1 along that axis") are the
**<Term id="basis vector">basis vectors</Term>**, the agreed unit that makes the numbers mean a real
direction.

<Callout type="tip">
**Infra bridge.** This is serialization. The arrow is the rich object; the components are the
**wire format** — a flat list both sides agree how to read. The basis vectors are the *protocol*:
sender and receiver agree the first number means "along x," and the integers suddenly mean
something. The chip only ever ships the flat list.
</Callout>

You'll essentially never touch basis vectors operating ML systems — but they're *why* a flat list
of numbers can stand in for a real object, which is the same reason a **wrong shape, not a wrong
value, is what usually breaks a run**.

## Rank — how many dimensions

The one number that classifies a tensor is its **<Term id="rank">rank</Term>**: how many
dimensions it has, i.e. **how many indices you need to reach a single value**.

- **rank 0** — a **<Term id="scalar">scalar</Term>**, one number, shape `()`.
- **rank 1** — a **<Term id="vector">vector</Term>**, a list, shape `(n,)` — the `[x, y, z]` above.
- **rank 2** — a **<Term id="matrix">matrix</Term>**, a grid, shape `(rows, cols)`.
- **rank 3+** — a cube and beyond, like `[batch, seq, hidden]`.

<Callout type="warning">
**One naming trap.** "Rank" here means **number of dimensions** (you'll also see *ndim* or
*order*). It is **not** the linear-algebra "rank of a matrix" (the count of independent rows). Same
word, unrelated idea — when an ML tool says a tensor is "rank 3," it means three axes.
</Callout>

### A tensor you already know — a digital image

Forget arrows for a second. A **digital image is a tensor**, and it shows you every rank at once:

| what it is | shape | rank | each value is |
| --- | --- | --- | --- |
| one grayscale pixel | `()` | 0 · scalar | a brightness, `0` (black) → `255` (white) |
| a row of pixels | `(width,)` | 1 · vector | one brightness each |
| a grayscale photo | `(height, width)` | 2 · matrix | a grid of brightnesses |
| a color photo | `(height, width, 3)` | 3 · 3-tensor | three numbers per pixel — **R, G, B** |
| a batch / a video's frames | `(n, height, width, 3)` | 4 · 4-tensor | the same, stacked |

A grayscale photo is *literally* a grid of brightness numbers — one per pixel. Now make it color: you
don't get a new picture, you get a **third dimension** — a new axis called **channels**. The same grid,
but **three values deep** — how much red, green, and blue sit at each pixel. That channels axis is
exactly the jump from a matrix to a rank-3 tensor. Stack a batch of photos (or a video's frames) and you've added a fourth.

Walk an image up the ranks yourself — one pixel, a row, a grayscale grid, then color (the **+RGB
channels** dimension), then a stack of frames — and watch the stored array grow right alongside it:

## Why rank is the scariest word in a memory budget

Here's the operational punchline. Each dimension you add doesn't *add* to the size — it
**multiplies** it. The number of elements is the product of the dimensions, so growth is
**multiplicative**, not additive.

Make it concrete at model scale — every dimension `4096` wide, in `bf16` (2 bytes each):

| rank | shape | elements | bytes |
| --- | --- | --- | --- |
| 1 | `(4096,)` | 4 K | 8 KiB |
| 2 | `(4096, 4096)` | 16 M | 32 MiB |
| 3 | `(4096, 4096, 4096)` | 69 B | **128 GiB** |

One extra dimension took the same kind of data from **32 MiB to 128 GiB** — past a single
accelerator's **<Term id="hbm">HBM</Term>** (today's high-end parts hold ~80–140 GB). Nothing changed
but the rank.

<Callout type="tip">
**Infra bridge.** This is why "just add a dimension" terrifies the people sizing the cluster.
**Activations** (the chip's intermediate scratch values for each layer) and the **KV-cache** (a
per-token scratchpad attention keeps in HBM to avoid recomputing earlier tokens) both carry batch
*and* sequence *and* hidden dimensions — every one a multiplier. When a job OOMs on a longer context
or a bigger batch, you're watching this table play out — HBM utilization climbs until the run dies.
The element count, not the dtype, is usually the culprit.
</Callout>

For operating ML systems, the array definition is all you need: **a tensor is a multidimensional

## Why this matters

- **It's the vocabulary for everything else.** Shapes, padding, precision, sharding — all of it is
  "what's the rank and the shape, and how many bytes does that come to."
- **Rank drives the memory bill.** Sizing HBM, predicting an OOM, reading why a longer sequence
  blows up — all start with "how many dimensions, each how big, times the dtype."
- **The chip stores a flat array.** No arrows, no geometry at runtime — just a row of numbers and a
  shape. That's why a wrong shape, not a wrong value, is what usually breaks a run — and the next
  lesson, on **tensor shapes**, shows how to compute that footprint before a job ever starts.
