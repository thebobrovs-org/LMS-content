## The one-line summary

Every infra engineer meets `bf16`, `fp16`, `fp4` and assumes the ML team is being
fashionable. They're not — this is the most systems-y decision in the whole stack. **A
number's byte width is a throughput lever.** Halve the bytes a value occupies and you halve
the traffic it puts on the memory bus, which **doubles its
<Term id="arithmetic intensity">arithmetic intensity</Term>** and keeps the expensive matrix
unit *fed* instead of *starved*. The price is range and precision — and getting that wrong
makes a training run silently blow up. This is the first number you reason about when you size
memory or pick a config.

## A float is range *plus* precision

A floating-point number splits its bits into two jobs:

- the **exponent** sets the **<Term id="dynamic range">dynamic range</Term>** — how big or how
  small the value can get before it overflows to `inf` or underflows to `0`;
- the **<Term id="mantissa">mantissa</Term>** sets the **precision** — how finely it can tell
  nearby values apart.

<Callout type="tip">
**Infra bridge.** This is a wire-format choice, nothing more — like picking `int32` vs `int64`,
or a compact serialization. You're deciding how many bytes each number costs and what you give
up to shrink it. Two knobs: *reach* (exponent) and *resolution* (mantissa).
</Callout>

## bf16: range over precision

<Term id="fp32">fp32</Term> spends 4 bytes: an 8-bit exponent (huge range) and a 23-bit
mantissa (fine precision). **<Term id="bf16">bf16</Term>** keeps the *full 8-bit exponent* — the
same reach as fp32 — and throws away mantissa bits to fit in **2 bytes**. The other 16-bit
float, **<Term id="fp16">fp16</Term>**, makes the opposite bet: more mantissa, but only a 5-bit
exponent, so it **overflows to `inf` past ~65,504**.

Why training picks range: the values in a model span a *huge* dynamic range — tiny **gradients**
(the per-step correction signals) near `1e-7` up to **activations** (the intermediate values
flowing through the model) near `1e5` — and only an 8-bit exponent covers both. The coarser bf16
precision averages out over millions of updates (rounding is random noise that cancels); lost
*range* does not — one overflow to `inf` poisons everything downstream, and the run diverges.

## Why fewer bytes = a faster chip

Smaller isn't just cheaper to store — it's the lever that keeps the chip busy. The matrix unit
can do far more math per second than <Term id="hbm">HBM</Term> can deliver bytes, so the real
question is **<Term id="arithmetic intensity">arithmetic intensity</Term> = FLOPs
(floating-point math ops) ÷ bytes moved.** Halve the bytes per number and you roughly *double* the intensity for the same math —
pushing the workload from **memory-bound** (the <Term id="mxu">matrix unit</Term> idling, waiting on the
bus) toward **compute-bound** (the matrix unit saturated, which is what you paid for).

That's the <Term id="roofline">roofline</Term>: below the ridge you're starved on bandwidth,
above it you're saturating compute. Lower precision is one of the main levers that gets you over
it. Same value slider, now read off how byte width moves the workload across the ridge:

## fp4 and where this is going

The trend only goes one way: fewer bytes. **<Term id="fp4">fp4</Term>** (the OCP `E2M1` variant —
1 sign, 2 exponent, 1 mantissa) is arriving on the newest accelerators and runs at ~¼ bf16's bytes,
roughly doubling throughput. The catch the sim makes obvious: with one mantissa bit and a ~0.5–6 range, fp4 rounds
or overflows almost everything *raw* — so in practice values are **scaled into range** first. It's
a throughput bet you take where you can afford the resolution loss (inference, parts of training).

One detail that ties it together: the matrix unit multiplies in low precision but **accumulates partial
sums in fp32** — a matmul builds each output by adding up a long string of products, and keeping
that running sum in fp32 means the rounding doesn't pile up. You get the bandwidth win on the
inputs without the running sum drifting.

## Why this matters

Every memory and throughput decision you'll make starts here. **Picking the precision** sets your
HBM footprint (bf16 halves a checkpoint vs fp32) and your effective bandwidth (fewer bytes = more
intensity). **Reading a roofline** tells you whether to reach for lower precision or a bigger batch.
And when a run dies in `NaN`s, "did someone push it into fp16 and overflow?" is a real first
question. The engineer who treats number formats as ML trivia guesses; the one who sees them as a
byte-width-vs-range trade can size and debug the system.

Where's the dial? Precision is usually the **ML team's training-config flag** — you'll *see*
`bf16`/`fp16`/`fp8` in the run config rather than flip it yourself — and arithmetic intensity isn't
on a standard Grafana board; you read it off the **roofline and the profiler's MFU**, not a scraped
metric. Your job isn't to set the dial — it's to recognize the trade, size the memory it implies, and
spot the failure mode (the `inf`/`NaN` overflow) when it shows up.
