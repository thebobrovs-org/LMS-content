# 3.1 The agent loop: reason, act, observe

## Why / What / How
- **Why:** Every hard production problem with agents (reasoning loops, slow tools, wrong tool picks, runaway cost) is a property of the loop. You cannot debug what you cannot trace.
- **What:** How a model turns a goal into tool calls: function declarations, the model's proposed call, the runtime executing it, and the result fed back.
- **How:** Step through one request turn by turn: the model reads instructions and tool declarations, emits a function call, the runtime (not the model) executes it, the result returns as context, and the loop ends on a final answer or a stop condition (max iterations, escalation).

## Learning objectives
After this topic the learner can (ids become the lesson's `objectives`):
- `trace-loop`: Trace a multi-step request through each model call and tool call.
- `who-executes`: Explain that the model proposes a tool call and the runtime executes it.
- `stop-conditions`: Name the conditions that end a loop and the symptom when none fires.

## Must-learn (keep nothing else but this)
1. The model never runs a tool. It emits a structured call; your code or the runtime runs it.
2. Tool descriptions are prompts: vague names and docstrings cause wrong tool choices.
3. Every loop needs a stop condition. A loop without one burns tokens and time (the reasoning-loop failure in 4.4).

## Key terms (glossary)
- `function calling`: The model outputs a structured request to call a declared function with arguments.
- `function declaration`: The name, description and parameter schema that tell the model a tool exists.
- `ReAct`: A reason-then-act pattern in which the model alternates thoughts and tool calls.
- `max iterations`: A cap on loop turns that stops a runaway agent.
