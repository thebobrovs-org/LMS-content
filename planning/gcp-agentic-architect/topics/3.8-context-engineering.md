# 3.8 Context engineering at scale

**Topic id:** `agentic-ai/context-engineering` · **Level:** 400 · **Difficulty:** advanced · **Est:** 30 min
**Track:** S3 Custom agents · **Exam objective:** 3.1, 3.2, 4.2 · **Persona:** `personas/agentic-ai.md`
**Status:** plan-approved

## Why / What / How
- **Why:** At production scale, what goes into the context window decides quality, latency and cost. Tool sprawl, bloated history and over-retrieval are expert-level failure modes the earlier topics only hint at.
- **What:** Budgeting the context window: instructions, tool declarations, history, memory and retrieved content; limiting exposed tools; summarising or compacting history; recalling memory selectively; context caching; measuring the effect.
- **How:** Take the support agent at 10x traffic and 40 tools, measure tokens per turn by component, then cut them step by step (tool filtering, history compaction, selective memory, caching) and show the quality and cost effect of each.

## Learning objectives
After this topic the learner can (ids become the lesson's `objectives`):
- `context-budget`: Break a turn's context into components and find the largest.
- `reduce-context`: Choose a technique to reduce each component without losing quality.
- `measure-effect`: Verify a context change with evaluation, not intuition.

## Must-learn (keep nothing else but this)
1. Every token in context costs latency and money and can distract the model.
2. Expose only the tools a step needs; many tools degrade tool choice.
3. Prove each context change with the evalset before shipping it.

## Key terms (glossary)
- `context window`: The tokens a model sees in one call.
- `context caching`: Reusing a processed prompt prefix across calls to cut cost and latency.
- `history compaction`: Summarising or trimming earlier turns.
