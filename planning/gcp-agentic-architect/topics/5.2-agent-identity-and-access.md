# 5.2 Agent Identity and least-privilege access

**Topic id:** `agentic-ai/agent-identity-and-access` · **Level:** 200 · **Difficulty:** intermediate · **Est:** 30 min
**Track:** S5 Secure and govern · **Exam objective:** 5.1, 3.2 · **Persona:** `personas/agentic-ai.md`
**Status:** on staging

## Why / What / How
- **Why:** An agent running as a broad service account turns any prompt injection into a breach. Per-agent identity and boundaries contain the damage.
- **What:** Agent Identity (a SPIFFE-based principal per agent, certificate-bound tokens), IAM roles for agents, and Principal Access Boundary (PAB) policies that cap what an agent can ever reach.
- **How:** Take an agent from a shared service account to its own identity with narrow roles and a PAB policy; show what a hijacked prompt can and cannot reach at each step.

## Learning objectives
After this topic the learner can (ids become the lesson's `objectives`):
- `agent-identity`: Explain what Agent Identity provides over a shared service account.
- `least-privilege`: Grant an agent the narrowest roles its tools need.
- `pab`: Use a Principal Access Boundary policy to cap an agent's reach.

## Must-learn (keep nothing else but this)
1. Give each agent its own identity so access and audit are per agent.
2. Roles grant; a Principal Access Boundary caps. Use both.
3. Assume prompt injection will happen and design so it cannot reach much.

## Key terms (glossary)
- `Agent Identity`: A per-agent identity on Google Cloud, based on SPIFFE, with its own credentials.
- `SPIFFE`: An open standard for workload identities.
- `Principal Access Boundary`: An IAM policy limiting which resources a principal can access, regardless of grants.
